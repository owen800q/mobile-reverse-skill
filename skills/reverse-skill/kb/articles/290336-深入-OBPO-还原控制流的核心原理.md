*** 本文由 AI 阅读 OBPO 代码后撰写**

OLLVM 的控制流平坦化（Control Flow Flattening，下称 CFF）大概是前几年移动安全领域遇到最多的代码混淆方案。它的原理不复杂：把函数里所有基本块拆散，塞进一个由状态变量驱动的 `switch-loop` 结构里，让原本的顺序执行和分支跳转全部变成"修改状态变量 → 回到分发器 → 跳到下一个 Case"。效果也很直接——反编译器输出一个巨大的 `while-switch`，控制流图变成一朵以分发器为圆心的菊花图，原始的程序逻辑被彻底打散。

假设原始函数的控制流是这样的：

![image](https://bbs.kanxue.com/upload/attach/202603/715510_Z4MA6JE3EQZ66PG.webp)

经过 CFF 混淆后，变成了这样：

![image](https://bbs.kanxue.com/upload/attach/202603/715510_JCJH5PJ4TBDWM6A.webp)

所有块的原始连接关系全部消失，取而代之的是每个块都从 Dispatcher 出发、再跳回 Dispatcher 的星形拓扑。

对于分析者而言，手动恢复一两个函数并不困难，但当目标里有几百个被平坦化的函数时，自动化就成了刚需。obpo 就是为此而生的工具，它工作在 IDA Hex-Rays 的 Microcode 中间表示上，通过分析和修改 Microcode 的控制流图（CFG），让反编译器自己输出正确的伪代码。

本文将介绍 obpo 内部的处理思路与实现方法。由于 obpo-core 并未开源，文中以阐述原理和设计思路为主。

## 为什么在 Microcode 上做

在二进制层面做反混淆通常有两种路径：直接 patch 二进制指令，或者修改反编译器的中间表示。

patch 二进制的好处是直观，但问题也很多：不同架构的指令集差异巨大，需要处理指令编码、对齐、重定位等细节，还要考虑分支距离溢出等工程问题。

Hex-Rays 的 Microcode 是一种统一的中间表示，不管底层是 ARM、x86 还是 MIPS，到了 Microcode 层面都是同一套指令集和 CFG 结构。在这里做修改有几个好处：

1. **跨架构**，一套逻辑适配所有 IDA 支持的处理器。
2. **直接影响反编译结果**，修改 Microcode CFG 后，Hex-Rays 的后续优化 pass 和类型推断会自然地基于修正后的 CFG 继续工作，最终输出干净的伪代码。
3. **不污染二进制文件本身**，所有修改都发生在内存中的中间表示上。

obpo 选择在 `MMAT_GLBOPT1`（全局优化阶段）的 Microcode 上工作。这个阶段足够成熟——常量传播和简单的死代码消除已经完成，能减少很多混淆引入的噪声；同时又不至于太晚，CFG 结构还保持着与原始控制流的对应关系。在整个 Hex-Rays 的处理流水线中，obpo 的介入位置大致如下：

## 怎么看待这个问题

在介绍具体步骤之前，先定义几个贯穿全文的概念。

一个被 CFF 混淆的函数，其 Microcode CFG 可以被划分为三个部分：

### Dispatcher

Dispatcher 是平坦化的核心——由一组基本块构成的分发网络。它读取状态变量，进行比较或计算，然后通过一系列条件跳转把控制流导向不同的 Case。一个典型的 Dispatcher 可能只是一个 `switch` 的展开形式（一连串 `if-else`），也可能是多层嵌套的比较树。

Dispatcher 内部的指令可以分为两类：

- **计算指令（Calculation）**：对状态变量进行赋值、运算。
- **分发指令（Dispatch）**：消费状态变量值的条件跳转。

### Case

Case 是原始程序的一个基本块（或一段连续的基本块），是真正承载业务逻辑的部分。在混淆后的 CFG 中，Case 从 Dispatcher 的某个出口被跳入，执行完自己的逻辑后，会修改状态变量的值，然后跳回 Dispatcher，由 Dispatcher 决定下一步去哪个 Case。

一个 Case 可能很简单（只有一条赋值语句），也可能包含复杂的控制流（内部的 if-else、循环等）。所以 Case 有自己的入口和出口——入口是从 Dispatcher 跳入的第一个块，出口是最终跳回 Dispatcher 的那个块。

在 obpo 的术语中：

- **Out Block**：Case 的入口块，即 Dispatcher 的"出口"。它是 Dispatcher 的后继，但它不支配任何 dispatch block——换句话说，它是控制流真正离开 Dispatcher 内部判断逻辑的地方。
- **Exit Case**：那些不会再跳回 Dispatcher 的 Case（比如函数的 `return`）。

### Flow

如果把上面的结构画出来，核心问题就很清楚了：

![image](https://bbs.kanxue.com/upload/attach/202603/715510_BUBMB4GC6KJS5RC.webp)

混淆后的 CFG 里，Case A 执行完之后并不是直接跳到 Case B，而是把状态变量改成 `Y`，跳回 Dispatcher，Dispatcher 再根据 `state == Y` 跳到 Case B。我们要做的就是**把中间绕了一圈 Dispatcher 的间接跳转，还原成 Case A → Case B 的直接跳转**。

这个"Case A 的出口，经过 Dispatcher，到达 Case B 的入口"的一条完整路径，就是一个 **Flow**。准确地说，一个 Flow 记录了：

- 从哪个 Case 出发（`start_block`）
- 在哪个位置跳入 Dispatcher（`edge`：从 `edge.src` 跳到 `edge.dest`）
- 经过哪个 Dispatcher 入口（`dispatch_block`）
- 最终到达哪个 Case 入口（`dest_block`，即目标 Out Block）
- 以及这条路径上完整的执行轨迹（emulation trace）

**整个 obpo 的工作，就是找到所有的 Flow，然后根据 Flow 把 CFG 缝回去。**

## 找到 Dispatcher

要恢复控制流，第一步是搞清楚哪些块是 Dispatcher 的一部分，哪些块是 Case 的一部分。

### 种子标记

obpo 需要用户标记至少一个 Dispatcher 中的条件跳转指令作为种子。这个标记不需要特别精确——只要是 Dispatcher 中任意一个条件跳转块即可。用户可以标记多个。

拿到种子之后，从它所在的块中提取出尾部的条件跳转指令，作为分析的起点。

### 数据流追踪

仅凭一个种子是不够的——Dispatcher 通常由多个块组成，我们需要找到所有参与分发逻辑的块。方法是利用状态变量的数据流关系，从种子出发，双向扩展。

首先，obpo 自己实现了一套基于块级别的 UD/DU Chain（Use-Definition / Definition-Use Chain）。为什么不直接用 IDA 自带的数据流分析？因为这里需要的是一个轻量的、能以"变量在哪个块被定义/使用"为粒度进行查询的链，而不是 IDA 内部用于优化的完整数据流信息。自实现的 `DataFlowChains` 在整个 MBA 上做一次前向传播，就能得到所有块之间的变量定义-使用关系。

有了 UD/DU Chain，从种子开始做交替的双向追踪：

**反向追踪**：从种子指令出发，沿着 UD Chain 向上查找——这条条件跳转用到了哪个变量？这个变量是在哪里被赋值的？赋值指令又用到了哪些变量？一路追上去，就能找到所有参与状态变量计算的指令（Calculation Instructions）。

**正向追踪**：从找到的计算指令出发，沿着 DU Chain 向下查找——这个计算结果被谁使用了？如果使用者是一个条件跳转指令，那它就是一个新的分发指令（Dispatch Instruction）。

这两个方向的追踪交替进行，直到不再有新的指令被发现。这是一个类似不动点的迭代过程，伪代码大致如下：

```
work_list = [seed]

while work_list:

    old_calculations = set(calculation_instructions)

    backward_track(work_list)          # 扩展 calculation_instructions

    new_calculations = calculation_instructions - old_calculations

    old_dispatches = set(dispatch_instructions)

    forward_track(new_calculations)    # 扩展 dispatch_instructions

    new_dispatches = dispatch_instructions - old_dispatches

    work_list = new_dispatches
```

追踪结束后，所有 Dispatch Instruction 所在的块构成 `dispatch_blocks` 集合。

## 划分边界

找到了 Dispatcher 的所有块之后，下一步是把 CFG 中的其他块进行分类。在这个过程中，支配树（Dominator Tree）分析扮演了核心角色。

> 补充一个图论概念：
>
>

> - **A 支配 B (A dominates B)**：意味着在 CFG 中，从起点到达 B 的每一条可能路径，都**必须**经过 A。
>

> - 反过来就是：**B 的支配者中包含了 A**。
>

### Dispatch Entry 与 Prologue

**Dispatch Entry** 是整个分发网络的唯一入口点。在所有 dispatch blocks 中，如果有一个块**支配了其他所有的 dispatch block**，那它就是 Entry。直觉上，所有回跳到 Dispatcher 的路径，都必须在这个块汇合。

**Prologue** 是函数开头、在第一次进入 Dispatcher 之前对状态变量进行初始化的块。判断方法：对于包含计算指令（calculation block）的块，如果**它的支配者集合中没有任何 dispatch block**，说明到达它根本不需要经过分发逻辑，它自然处于整个分发网络“上方”的序言部分。

### Out Block 与 Exit Case

**Out Block** 的检测从 Dispatcher 的所有后继块出发，向外扩展：

1. 取 dispatch blocks 的所有后继块作为候选。
2. 如果候选块是一个不包含任何指令、只有一条跳转指令的空跳块（simple `goto`），且它能到达 dispatch blocks，则跳过它，并把它的后继加入候选。（这主要是为了剔除编译器或混淆器生成的一些无意义中转块，直达真正的业务入口）。
3. **关键判断**：检查候选块**是否支配了任何一个 dispatch block**（即该块的被支配节点集合与 dispatch_blocks 的交集是否为空）。
- 如果不为空：说明候选块是去往后续 dispatch block 的必经之路（或者它本身就是 dispatch block），它依然在 Dispatcher 的分发网络内部，跳过。
- 如果为空：说明通过它之后，控制流彻底离开了当前分发节点的控制，这就找到了真正的 **Out Block**——Dispatcher 的出口，也就是 Case 的入口。

为了直观理解第 3 点，考虑一个多层 `if-else` 展开的 Dispatcher 内部结构：

![image](https://bbs.kanxue.com/upload/attach/202603/715510_Q77B47BZFQ9M5B6.webp)

在这里，Block 4 和 Block 7 都是 Dispatch Block 3 的后继。那 Block 4 为什么不是 Case 入口（Out Block）呢？因为 **Block 4 支配了 Block 5**（到达 Block 5 必须经过 Block 4），而 Block 5 显然是属于分发逻辑的 dispatch block。这说明 Block 4 依然在分发网络的内部骨架上。相反，Block 7 和 Block 8 没有支配任何 dispatch block，所以它们才是真正的 Out Block。

最后，在找出的 Out Block 中，如果一个块无法再到达任何 dispatch block（即不会再跳回 Dispatcher），它就被标记为 **Exit Case**，通常对应着函数的 `return` 或异常退出块。

### 分类结果

沿用前面的贯穿示例，分析完成后，CFG 中的每个块都被分配到了明确的区域：

![image](https://bbs.kanxue.com/upload/attach/202603/715510_Y3VMJYW66NAVEXX.webp)

| 分类 | 块 | 判定依据 |

|------|-----|----------|

| Prologue | Block 0 | 其支配者集合中没有任何 dispatch block |

| Dispatch Entry | Block 3 | 支配了集合中所有的 dispatch blocks |

| Dispatch Block | Block 5 | 包含 dispatch instruction |

| Out Block | Block 7 | Dispatcher 的后继，且**不支配**任何 dispatch block |

| Out Block + Exit Case | Block 8 | 不支配任何 dispatch block，且无法到达 Dispatcher |

到这里，CFG 被清晰地划分成了三个区域：Prologue、Dispatcher、Cases。接下来的任务是弄清楚 Case 之间真正的执行顺序。

## 恢复真实控制流

这是整个方案中最关键的一步：确定每个 Case 执行完之后，真正应该跳转到哪个 Case。

### 思路

一个 Case 执行完毕后会把状态变量设置成某个值，然后跳回 Dispatcher。Dispatcher 根据这个值做一系列条件判断，最终跳到下一个 Case。如果我们能"模拟执行"这个过程——从 Case 的出口开始，带着 Case 设置的状态变量值，走一遍 Dispatcher 的条件跳转链，看它最终会落到哪个 Out Block——那我们就知道了这个 Case 的真正后继。

### Microcode Emulator

obpo 实现了一个轻量的 Microcode 解释器（MCEmulator）来完成这个模拟。它不是一个通用的完整模拟器——它只关心与 Dispatcher 相关的指令。

具体来说，MCEmulator 维护了两个简单的空间：寄存器空间和内存空间。它的执行策略是：

![image](https://bbs.kanxue.com/upload/attach/202603/715510_2GEGTXK2SGZYS5W.webp)

这个策略让模拟器专注于状态变量的传播和 Dispatcher 的判断逻辑，忽略所有不相关的计算。因为 CFF 混淆的本质就是把状态变量计算和条件分发叠加在原始逻辑上，只要我们能准确地模拟这些叠加的部分，就能还原出真实跳转。

### FlowFinder

`FlowFinder` 用模拟器从每个可能的起点出发，寻找它的目标 Out Block，产出 Flow。

#### 探索式寻路

首先尝试一种"探索式"的方法：从 Prologue 的入口开始，用一个空的模拟器执行。模拟器走过 Prologue（在这里，Prologue 中对状态变量的初始赋值会被执行），然后进入 Dispatcher，经过一系列条件跳转，最终到达第一个 Out Block——假设是 Case A。

到达 Case A 之后，模拟器继续从 Case A 开始执行。Case A 内部的业务逻辑被跳过，但 Case A 末尾对状态变量的赋值会被执行。然后模拟器跳回 Dispatcher，经过条件判断，到达下一个 Out Block——比如 Case B。

这样一路"探索"下去，每经过一次"Case → Dispatcher → 下一个 Case"的过程，就产生一个 Flow。

在这个过程中，如果遇到 Case 内部的分支逻辑怎么办？

#### 处理分支

其实无论是探索式寻路还是后续的补全模式，底层的单次寻路都由 `EmuPathFinder` 执行，它自身就具备处理内部 `if-else` 的分叉能力。

当模拟器在某个非 Dispatcher 的条件跳转处遇到 `UnknownBranch` 时（即 Case 内部的 `if-else`），`EmuPathFinder` 会在内部就地分叉：对这个条件跳转的每个后继分支，复制一份当前的模拟器状态，分别继续模拟，看看每条路各自通向哪个 Out Block。

考虑一个包含内部分支的 Case：

![image](https://bbs.kanxue.com/upload/attach/202603/715510_NR6FEUG5EJ28CKX.webp)

模拟器执行到 Block 7 的 `if (x > 10)` 时，这不是 Dispatcher 的条件跳转（不在白名单中），于是抛出 `UnknownBranch`。`EmuPathFinder` 将当前模拟器状态复制两份，分别从 `true` 和 `false` 分支继续执行：

- **分支 1** (true)：经过 Block 7a → `state = 0xD` → Block 10 → Dispatcher → 到达 Block D。产出 Flow: `(10 → Dispatcher) → D`
- **分支 2** (false)：经过 Block 7b → `state = 0xE` → Block 10 → Dispatcher → 到达 Block E。产出 Flow: `(10 → Dispatcher) → E`

这本质上是一个带状态的广度优先搜索。搜索空间是条件跳转的分支组合，在每个分叉点展开所有可能性，直到到达某个 Out Block。为了避免无限循环，`EmuPathFinder` 使用"已访问状态集"进行去重——对于同一个起点，如果模拟器的寄存器和内存状态都相同，就不再重复探索。

#### 补全模式

即使 `EmuPathFinder` 具备分叉遍历所有分支的能力，这种多米诺骨牌式的**探索式连贯寻路（_finder_by_explore）**仍可能会有遗漏。如果中间某条路径因为混淆器设下的不可模拟陷阱、异常跳转或遇到解析不了的未初始化值，导致模拟器报错并中断，那么这条线索就断了。这会导致其后续的 Case 失去成为下一个探索起点的机会，从而产生遗漏。

因此，如果探索式方法结束后发现还有在静态边界划分中找到的 Out Block 没能找到它的后继（并且不是 Exit Case），FlowFinder 就会启动**补全模式**。它先让 Prologue 所有的执行路径汇聚，在到达 Dispatcher 时的状态做交集，得到一个保守的"初始化快照"——包含了 Prologue 共同确定下来的基础寄存器/内存值。然后，打破连贯执行的限制，直接把每一个 Out Block 都作为独立的起点，配合这个快照状态，强行做一遍点对点寻路，以此补全所有未发现的 Flow。

### 从轨迹中提取 Flow

模拟器到达目标 Out Block 后，留下了一条完整的执行轨迹（经过了哪些块、哪些指令）。`FlowFinder` 需要从这条轨迹中提取出关键信息，构造 Flow 对象。

核心是 `resolve_jump_block`：沿着轨迹中经过的块序列，从头往后扫描，找到第一个属于 Dispatcher 且不是 Out Block 的块——这就是进入 Dispatcher 的位置。然后取它前面那个块作为"跳入点"。

![image](https://bbs.kanxue.com/upload/attach/202603/715510_VFAHVQDHJN4UYCT.webp)

上图中，`resolve_jump_block` 从头扫描轨迹 `[7, 3, 5, 8]`，Block 3 是第一个 Dispatcher 块且不是 Out Block，所以 `edge = (7 → 3)`。最后到达的 Block 8 就是 `dest_block`。

产出的 Flow：

```
Flow {

    start_block: 7      // 从哪个 Case 出发

    edge: (7 → 3)       // 在哪跳入 Dispatcher

    dispatch_block: 3    // 经过的 Dispatcher 入口

    dest_block: 8        // 到达的目标 Out Block

    trace: [7, 3, 5, 8]  // 完整执行轨迹

}
```

### 一个完整的寻路过程

沿用前面的例子，FlowFinder 的探索式寻路过程如下：

![image](https://bbs.kanxue.com/upload/attach/202603/715510_MNJXVFHC5F8VTXA.webp)

第一轮从 Prologue 出发，模拟器执行 `state = 0xA`，进入 Dispatcher，Block 3 判断 `state==0xA` 为真，跳到 Block 7（Case A）。产出 Flow：`(0 → 3) → 7`。

第二轮从 Case A（Block 7）出发，模拟器执行 `state = 0xB`，跳回 Dispatcher，Block 3 判断 `state==0xA` 为假，继续到 Block 5，判断 `state==0xB` 为真，跳到 Block 8（Case B）。产出 Flow：`(7 → 3) → 8`。

Block 8 是 Exit Case，不会再跳回 Dispatcher，探索结束。所有 Flow 汇总如下：

| Flow | start_block | edge | dest_block | 含义 |

|------|-------------|------|------------|------|

| #1 | Block 0 | (0 → 3) | Block 7 | Prologue → Case A |

| #2 | Block 7 | (7 → 3) | Block 8 | Case A → Case B (exit) |

## 缝合

拿到所有 Flow 之后，最后一步是根据 Flow 修改 Microcode 的 CFG，把间接跳转恢复为直接跳转。

### 处理共享路径

在缝合之前，有一个需要预处理的问题：多个 Case 可能共享 Dispatcher 内部的某些块。

考虑这种情况：Case A 和 Case C 的出口都需要经过 Block 10（一个 Dispatcher 前的公共计算块），然后从 Block 10 跳入 Dispatcher。如果直接 patch Block 10 的跳转目标，Case A 的 patch 会破坏 Case C 的控制流。

![image](https://bbs.kanxue.com/upload/attach/202603/715510_QZ3WYP8BGGAJNY6.webp)

`SplitCommonPatcher` 解决这个问题的方法是**克隆**。对于每个 Case（按 `start_block` 分组），检查它的 Flow 轨迹中是否包含了不被 `start_block` 支配的块——这些就是与其他 Case 共享的块。将这些共享块克隆一份，让每个 Case 拥有自己独立的副本，然后更新 Flow 中的引用。

克隆完成后，每个 Flow 的 `edge.src` 都指向了独立的块，互不干扰，可以安全地 patch。

### 三种 Patch 策略

`FlowPatcher` 按 `edge`（跳入 Dispatcher 的边）将所有 Flow 分组。同一个 edge 出发的 Flow 可能指向一个或多个不同的 `dest_block`。根据情况，采用不同的策略：

#### 单目标：直接跳转

如果从同一个 edge 出发的所有 Flow 都指向同一个 `dest_block`，最简单——直接把 `edge.src` 的跳转目标从 Dispatcher 改为 `dest_block`。

![image](https://bbs.kanxue.com/upload/attach/202603/715510_CCT58G8G9WBEY2W.webp)

#### 多目标：先尝试拆分

如果同一个 edge 出发的 Flow 指向多个不同的 `dest_block`，说明原始代码在这里存在条件分支。obpo 对多目标的处理不是一步到位，而是一个**先拆分、再兜底**的两级策略。

首先尝试拆分：如果 `edge.src` 恰好有多个前驱（且只有一个后继），并且不同前驱对应的 Flow 确实指向了不同的目标，那么就把 `edge.src` 按前驱克隆成多份，每个前驱连接自己的副本，然后对每组**递归调用** `run()`——这样原本的一个多目标问题就被拆分成了多个单目标（或至少更简单的多目标）问题。

![image](https://bbs.kanxue.com/upload/attach/202603/715510_FA5R6TWMHPVQ8SY.webp)

#### 多目标：兜底构造迷你 Dispatcher

如果拆分不适用（比如 `edge.src` 只有一个前驱，或者所有前驱都指向同样的多个目标），那就无法通过克隆来简化问题。这时才退而使用最后的手段：构造一个"迷你 Dispatcher"。

obpo 需要找到一个能区分不同目标的判别值。方法是：遍历所有 Flow 执行轨迹中共同使用过的操作数（operand），检查每个操作数在 `edge.dest`（进入 Dispatcher 的第一个块）处的模拟器状态中的值，找到一个能与 `dest_block` 形成一一映射的操作数。

找到判别操作数后，生成一个简化的条件跳转链来替代整个 Dispatcher：

![image](https://bbs.kanxue.com/upload/attach/202603/715510_MFT8BT969N94BXJ.webp)

这个迷你 Dispatcher 被插入到 CFG 中，替代原本跳向 Dispatcher 的那条边。相比原来要穿越整个 Dispatcher 网络，这里只需要一两条条件跳转。

### Trampoline

在 Dispatcher 内部，可能存在一些"真实指令"——不属于混淆逻辑、但被混淆器放在了 Dispatcher 块里的指令。如果直接跳过 Dispatcher，这些指令就丢失了。

obpo 通过 trampoline（蹦床块）解决这个问题：如果某个 `dest_block` 对应的多个 Flow 在 Dispatcher 路径上都经过了相同的真实指令，就创建一个蹦床块，把这些指令复制进去：

![image](https://bbs.kanxue.com/upload/attach/202603/715510_9XFARP7HS5X8ZV8.webp)

这样既跳过了 Dispatcher 的分发逻辑，又保留了夹杂其中的真实计算。

### Patch 后的效果

经过 FlowPatcher 的处理，所有经过 Dispatcher 的间接跳转都被替换为直接跳转（或简化的条件跳转）。对比开头的例子，原本的菊花图变回了结构化的控制流：

完成 patch 之后，obpo 会清理块类型标记，修复一些 Hex-Rays 内部数据结构的一致性问题（比如栈变量的 MBA 引用），然后将修改后的 MBA 缓存起来。Hex-Rays 的后续 pass 会基于这个修正后的 CFG 继续工作，最终输出干净的伪代码。

## 工程上的坑

实现过程中遇到了不少值得一提的问题。

### 数据流分析的取舍

为什么不用 IDA 自带的数据流分析，而要自己写 `DataFlowChains`？

IDA 内部的数据流分析是为编译器优化服务的，精度很高但粒度也很细——它追踪的是指令级甚至操作数级的信息。而 obpo 需要的是块级别的"变量 X 在哪些块被定义，在哪些块被使用"，用于驱动 Dispatcher 的双向追踪。

自实现的 DataFlowChains 有几个特点：

1. **块级别粒度**，每个块只有 `defs` 和 `uses` 两个集合，不关心块内具体哪条指令在操作。
2. **轻量**，一次前向传播即可完成。
3. **保守**，宁可多追踪一些不相关的指令（false positive），也不能漏掉真正的分发逻辑（false negative）。因为漏掉一个 dispatch block 意味着后续的 emulation 和 patching 都会出错。

### 模拟器的边界

MCEmulator 不需要完整模拟所有 Microcode 指令——它只需要模拟那些被标记为 Calculation 或 Dispatch 的指令。对于其他指令，直接跳过。这大大简化了实现，也避免了复杂指令（比如内存访问、函数调用）带来的模拟困难。

但这种策略有一个前提：状态变量的计算链必须是自包含的，不依赖于外部的复杂计算。幸运的是，OLLVM 标准的 CFF 实现确实满足这个条件——状态变量通常是一个局部整数变量，只通过简单的赋值和算术运算更新。

### 未初始化值

模拟器有时会遇到未初始化的值——某个寄存器或内存地址在之前的执行路径中从未被赋值。这通常发生在：

1. 模拟器从 Case 的中间开始执行（比如补全模式），此时 Case 内部对某些变量的赋值还没发生。
2. 状态变量的初始值来自函数参数或全局变量，模拟器没有上下文信息。

对于情况 1，obpo 通过 Prologue 快照（所有 Prologue 路径到达 Dispatcher 时的状态的交集）来提供部分初始状态。对于情况 2，通常意味着 CFF 有变体或者混淆器做了额外处理，需要更多的启发式方法。

### Hex-Rays 内部结构维护

修改 Microcode CFG 并非简单地改几个指针。Hex-Rays 内部有一套严格的一致性检查（`mba.verify`），包括：

- 块的 `predset` 和 `succset` 必须互相一致。
- 栈变量的 `mba` 引用必须指向当前的 MBA 对象。
- 块类型（`BLT_1WAY`、`BLT_2WAY` 等）必须与实际的跳转指令一致。

obpo 的 `MBAPatcher` 封装了块克隆、分支 patch、块插入等操作，每次操作后都确保 `predset`/`succset` 的双向一致性。最后还有一个 `MBAFixup` pass 来处理类似栈变量 MBA 引用之类的深层问题。

## 总结

回头看整个方案，它的有效性其实建立在一个观察上：**CFF 混淆只是在原始控制流上叠加了一层间接跳转，而这层间接跳转是确定性的——给定一个状态变量值，Dispatcher 的行为是完全确定的。**

所以 obpo 的思路是：不试图理解原始程序的语义，只需要模拟 Dispatcher 的行为，就能把这层叠加的间接跳转一条一条地解开。数据流分析定位 Dispatcher，支配关系划分边界，轻量模拟恢复跳转目标，最后 patch CFG。每一步都只做一件明确的事，组合起来就完成了还原。

这个方案也有它的局限：它假设状态变量的更新是局部的、可模拟的。如果混淆器把状态变量的计算与外部输入耦合（比如通过不透明谓词），或者使用非标准的分发结构（比如间接跳转表），就需要额外的处理。但对于标准的 OLLVM CFF 及其常见变体，这套方法已经足够有效。

这大概也是做工程的一个缩影：先识别问题的结构，找到一个能把问题分解的视角，然后逐步逼近答案。不需要一开始就想清楚所有细节——先把 Dispatcher 找出来，再把边界划清楚，再一条路一条路地模拟，最后把边缝回去。每一步都给下一步提供更清晰的信息，直到整个拼图完成。
