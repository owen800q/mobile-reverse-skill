## 前言

本人小白一枚，想尝试学习一些加固，在身边朋友的推荐下选择了这个壳子.恰巧最近论坛上也有很多大佬发布了自己的分析贴（比如[乐子人大佬的帖子](https://bbs.kanxue.com/thread-291069.htm)），只是复现下来后发现后续的dex vmp相关帖子比较少（很不幸只找到了[爱吃菠菜大佬的这篇帖子](https://bbs.kanxue.com/thread-270799-1.htm)，不过因为年代久远甚至指令结构都不同了），于是写篇帖子记录一下.

新人发帖，如有错误还望大佬指出.

帖子使用的样本不方便说出来，不过是今年的.（因为据说这个样本保护项开得多）

## Java层特征

![image](https://bbs.kanxue.com/upload/attach/202606/945286_2XGESSQDTM3BZGE.webp)

可以看到被vmp保护的方法调用了Lcom/fort/andjni/JniLib;类的一个native方法

![image](https://bbs.kanxue.com/upload/attach/202606/945286_P8Q63ZBQKDFJF7V.webp)

JniLib类中有很多种不同的native函数，显然是通过不同的函数签名来处理不同返回值的跳板函数. 既然这个类加载了libdexjni.so，那么这些native函数大概率就是被这个so注册的.

## Native层初探

通过BinaryNinja加载so（这里把so基址设为了0x12000000），尝试在函数表中搜索Java_来定位，发现没有结果.

扫了一眼导出表

![image](https://bbs.kanxue.com/upload/attach/202606/945286_W3M5EYEXDSV6DV8.webp)

虽然有些明显的名称混淆，但JNI_OnLoad这些关键函数还在，导出表应该是没有被保护的.

既然静态注册搜不到，那么这些native函数必然是动态注册的了.

直接来到JNI_OnLoad：

![image](https://bbs.kanxue.com/upload/attach/202606/945286_9JZ44CNCR2WH5UP.webp)

发现函数不可解析，应该是被保护了.

往上查找.init.array：

![image](https://bbs.kanxue.com/upload/attach/202606/945286_6MHT8ETNMV9M2YP.webp)

![image](https://bbs.kanxue.com/upload/attach/202606/945286_A6W4BCZGXJ9GAT6.webp)

对应的地址完全是空的，那么只可能是在更早执行的.init进行解密了.

先从dynamic里找到init地址

![image](https://bbs.kanxue.com/upload/attach/202606/945286_PC62FCR28RV5GNQ.webp)

![image](https://bbs.kanxue.com/upload/attach/202606/945286_8TXJ7TMHHTYK6WE.webp)

sub_125617dc分配了一块内存并复制了arg2的数据，数据大小被存储在了arg1 + 0x28.

而sub_1256150c主要是进行了数据解压（疑似还有其他操作，但我这个样本并没有执行到，就没去分析）：

![image](https://bbs.kanxue.com/upload/attach/202606/945286_ZE68QCXURENFVVK.webp)

解压算法是nrv2d，以上数据均来自init函数最开始的参数0x12561b48：

![image](https://bbs.kanxue.com/upload/attach/202606/945286_MA2WPG4YHN8FHTS.webp)

具体逻辑搞清楚了，修复就简单了.可选择：

1.直接使用支持nrv2d的库对0x120096d8处大小0x33dfd的数据进行解压；

2.在init函数运行完后直接dump下0x120096d8处大小0x7e500的数据.

得到解压数据后直接塞回so文件对应位置即可.

这里需要补充一段，完成这步之后BinaryNinja已经可以正常解析函数了，但是后面在使用ida分析so时发现虽然导入表和导出表正确，但ida未能将符号对应的函数解析完整：

![image](https://bbs.kanxue.com/upload/attach/202606/945286_T9XS3GAECKFMJ89.webp)

简单分析发现这是因为这个so的section被动了手脚：

![image](https://bbs.kanxue.com/upload/attach/202606/945286_JUPREC79RGAB3W3.webp)

节中将一个很大的区域标记成SHT_NOBITS扰乱了ida的分析，只需把type改成SHT_NULL(0)或者SHT_PROGBITS(1)即可使ida正常解析.

## 虚拟机入口分析

解压数据回填后，JNI_OnLoad已经可以正常反编译了，映入眼帘的便是三个函数调用.

![image](https://bbs.kanxue.com/upload/attach/202606/945286_NECKGX6B2QN87E8.webp)

挨个翻了一下，发现前两个函数都有很明显的控制流：

![image](https://bbs.kanxue.com/upload/attach/202606/945286_R4NUDZABKGAU42C.webp)

而第三个函数看上去非常清晰，并且一眼就能看到很多关键数据（为了方便直观这里稍微分析了一下）：

![image](https://bbs.kanxue.com/upload/attach/202606/945286_VE9UASE48UTKQGD.webp)

既然前两个函数不太好看，那么就先分析第三个函数好了.

这个函数很简单，首先sub_12010028初始化了一些全局对象：

![image](https://bbs.kanxue.com/upload/attach/202606/945286_CEHAW3XWWFJVZWD.webp)

初始化完成后就注册了JniLib类的native函数：

![image](https://bbs.kanxue.com/upload/attach/202606/945286_2QZREMWNKRBBHG4.webp)

既然要找的函数已经在这了，不妨直接进去看看吧：

![image](https://bbs.kanxue.com/upload/attach/202606/945286_82KM76WE72QR3GB.webp)

sub_12017adc就是虚拟机的入口了，这里命名为vm_entrance.

由上图不难看出，这个函数的签名大概是(JNIEnv* env, jobjectArray args, void* result)

到了这里，先回顾一下函数的入参：

![image](https://bbs.kanxue.com/upload/attach/202606/945286_PFTT7YVX3UNU7UF.webp)

jobjectArray第0位是jclass，若为实例方法则第1位是实例的jobject，最后一位jint是vm函数的idx.

![image](https://bbs.kanxue.com/upload/attach/202606/945286_CFYE35UA2J37TDU.webp)

入口函数先获取了jobjectArray最后一位的Integer，然后调用了intValue函数读到jint传给j__lSSO05lI$I5IllOl_0lS$_lllIII__l$IOlI55$O550IS__lS5$：

![image](https://bbs.kanxue.com/upload/attach/202606/945286_KJ4K57G9KCDA4WP.webp)

而这个函数通过vm_idx去查了表data_1255ff48，因此这个表里一定存储着所有vm方法的数据.

交叉引用可以看到另一个函数对这个表进行了很多操作，应该就是初始化了：

![image](https://bbs.kanxue.com/upload/attach/202606/945286_QHDTNXWD83XMXJ5.webp)

至于这个函数，我们在上面的流程里其实已经见过了，正是JNI_OnLoad调用的第一个函数.

既然终究是躲不过的话，就只好顶着控制流简单看一下喽：

![image](https://bbs.kanxue.com/upload/attach/202606/945286_RWVH7SW8J2JEGWW.webp)

这个表里的结构体大小是0x28，通过一些函数读取数据，读取格式是MessagePack：

![image](https://bbs.kanxue.com/upload/attach/202606/945286_YXEF5KXRMCX7YJB.webp)

这里偷懒用frida在这个函数初始化完后去遍历表data_1255ff48（这里只处理了libDexHelper.so的检测，libdexjni.so应该是没有检测的），根据打印出的数据，大概猜测结构体结构：

```
struct method_info __packed
{
    uint32_t idx;
    uint32_t code_item_size;
    void* code_item;
    uint32_t reg_count;
    uint32_t ins;
    uint32_t outs;
    uint32_t is_static;//这个没去验证，纯经验猜测
    char* shorty;
};
```

*注：这里的code_item是我先入为主瞎取的名字，并不是真正的标准code_item，因为这个vmp的字节码很像code_item的结构，具体长这样：

![image](https://bbs.kanxue.com/upload/attach/202606/945286_FD5R76H3FZF2DWA.webp)

而code_item_size则是这段字节码数据的size.

后面会对其进行详细分析，这个命名我感觉还是比较贴合的，就是有点容易混淆，因此提一嘴.

重新回到vm_entrance函数，可以看到在栈上重新排了一个结构体：

![image](https://bbs.kanxue.com/upload/attach/202606/945286_8ADV9GYJ6TF7AZ8.webp)

![image](https://bbs.kanxue.com/upload/attach/202606/945286_HDEBFSSS288TCPC.webp)

最终传入了函数sub_12018544.

sub_12018544大概扫了眼，应该是整理vm方法的参数，给包装类拆箱：

![image](https://bbs.kanxue.com/upload/attach/202606/945286_G6DPN5SSHMU9GHD.webp)

这里创建了一个大小0x48的结构体，与寄存器有关，偏移0x8处的列表用于存储寄存器

![image](https://bbs.kanxue.com/upload/attach/202606/945286_YK6FGU56348NHHC.webp)

![image](https://bbs.kanxue.com/upload/attach/202606/945286_T6XUUTVPKZ2KNDY.webp)

最终来到函数j__lIl_0ll5OIlIlISl00lI_lI5lIll$I$IIlIl00I$lIIIl5S0S5$

![image](https://bbs.kanxue.com/upload/attach/202606/945286_8399968T6RZCVZJ.webp)

跳到这个函数后binaryninja就有点不好使了，加载了半天也没加载好，控制流混淆得很严重：

![image](https://bbs.kanxue.com/upload/attach/202606/945286_DPE798UADHSNERQ.webp)

并且函数体量奇大，根据以上种种，不难猜到这个就是解释器函数了.

面对这一望无际的工作量，死磕明显不太现实.

尝试过写反混淆插件，但只能处理些简单的，效果不尽人意，若要兼容更多情况，插件工程量也相当大.

反混淆无果后，决定依靠trace. 试了下frida trace感觉不太稳定，经常会闪退，最后选择了unidbg trace.
