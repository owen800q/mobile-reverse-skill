## 问题

### 定位链路

如何定位系统定位的链路呢？
目前我们不知道APP的定位是从哪里来的,所以需要先把系统的LocationManager的入口铺满
安卓APP获取自身定位有两个方法
根据gp服务提供的`FusedLocationProviderClient`（融合定位提供器），常用函数有两个：
1.获取一次当前位置
**Java：`fusedLocationProviderClient.getLastLocation()`**，它返回设备**最后一次已知的缓存位置**，适合"打开页面时定位到当前位置"的场景（如地图初始化）。
2.持续监听位置变化
**`requestLocationUpdates(LocationRequest, LocationCallback)`**，在 `onLocationResult` 回调里拿最新坐标：

\```
val request = LocationRequest.Builder(
    Priority.PRIORITY_HIGH_ACCURACY, 2000  // 高精度，2秒一次
).setMinUpdateDistanceMeters(1f).build()

val callback = object : LocationCallback() {
    override fun onLocationResult(result: LocationResult) {
        result.lastLocation?.let { /* 处理 location */ }
    }
}
client.requestLocationUpdates(request, callback, Looper.getMainLooper())
// 不用时调用 client.removeLocationUpdates(callback) 停止
\```

还有系统原生方案:
框架自带的LocationManager:

- `getLastKnownLocation(LocationManager.GPS_PROVIDER)` —— 拿某提供商（GPS/网络）的最后已知位置
- 参数的值可能为gps network passive fused

- `requestLocationUpdates(...)` + `LocationListener.onLocationChanged(location)` 回调
国内大部分机器都没有或者不打开gp服务，因此一般采用高德/百度/腾讯的定位SDK，因为国内大多数安卓机都不预装GMS

层B:编译态如何让Hook失效
ART里一次方法调用的路径:
调用方进行方法调用的时候，都是同一个动作:
拿到目标方法的ArtMethod,读取它的entrypoint，跳过去执行
每个 `ArtMethod` 有一个执行入口字段：

\```
class ArtMethod {
  GcRoot<mirror::Class> declaring_class_;
  std::atomic<std::uint32_t> access_flags_;
  uint32_t dex_code_item_offset_;
  uint32_t dex_method_index_;
  uint16_t method_index_;
  uint16_t hotness_count_;
  struct PtrSizedFields {
    void* data_;                                  // native 方法时 = JNI entry
    void* entry_point_from_quick_compiled_code_;  // ← 执行入口
  } ptr_sized_fields_;
};
\```

`entry_point_from_quick_compiled_code_` 指向什么，决定这次调用怎么执行：

| 状态 | 何时进入 | entrypoint 指向 | 调用行为 |
|-|-|-|-|
| 解释执行 | 方法刚加载，还没被编译，或者一直为冷方法 | interpreter 解释器的入口桥接代码 | 每次调用都**读这个字段**再跳 |
| JIT/AOT 编译 | AOT:安装/更新APP是dex2oat提前编译进oat文件，JIT:运行时方法变热 | 该方法的机器码aot再oat文件中，JIT在JIT CODE cache里面 | 调用点**直接跳到机器码**，或已被内联 |
| deopt 后 | JIT 优化编译时会做乐观假设（比如“这个虚方法调用的接收者肯定是 X 类”于是去虚化+内联、“这个类型检查恒为真”）。运行时假设被打破（来了子类实例、加载了新类），优化代码没法继续跑，触发反优化：把栈上的优化帧拆开、还原成解释器帧 | 反优化入口桩deoptimization entry | 先走 deopt 处理，回解释器 |

Frida的HOOK做了什么呢？

\```
1. 找到目标 ArtMethod
2. 备份原 entrypoint
3. 把 entry_point_from_quick_compiled_code_ 换成自己的 native trampoline
4. 调用进入 trampoline → 转到 JS
\```

所以如果方法被JIT编译，并且调用点也被优化过，那么:

\```
编译后的调用方机器码：
    bl  0x7f12345678      ← 硬编码跳转到目标方法机器码

而不是：
    ldr x0, [art_method, #entry_point_offset]
    blr x0                ← 运行时读 entrypoint
\```

所以虽然改了ART里面的字段，但是bl根本不看它了
Hook对APP自身类失效了，因为梆梆java2c下这些方法被AOT/JIT编译，调用走已经生成的机器码，绕过了被替换的ArtMethod

层C
可以通过deoptimize才能hook到app的本身类
什么是deopt呢？
deoptimization 来自 JVM 世界的术语（HotSpot 的 deoptimization），指"从优化后的代码回退到未优化的解释执行状态"，同时**在回退时保留程序语义**（通过 deopt 时构造解释器栈帧，把寄存器/栈上的值搬到解释器帧里）
ART里面的deopt的几种触发:

- **显式 deopt**（调试器/Instrumentation）：`Instrumentation::DeoptimizeMethod` / `DeoptimizeEverything`
- **隐式 deopt**（运行时）：类型检查失败（`CheckCast`/`InstanceOf` 失败导致 inline cache miss）、`kAccSingleImplementation` 假设破裂、JIT 代码需要重新编译、GC 移动对象后代码修补等
- **调试相关**：attach debugger 时 ART 会 deopt 相关方法

ArtMethod里面,entrypoint指向哪里，决定它怎么跑：

\```
① 解释执行（interpreter）
   entrypoint ──► interpreter 入口
   每次调用：读字段 → 进解释器逐条执行 dex

② 编译执行（JIT / AOT）
   entrypoint ──► 该方法的机器码
   调用方往往被优化成：bl <硬编码地址> 或 inline cache 直接跳

③ deopt 状态
   entrypoint ──► deoptimization entry（一段 stub）
   调用进门先做"帧迁移"，然后跳解释器
\```

deopt就是把2放到3里面，deopt的入口是单独的，不能直接改成解释器入口，因为方法可能被其他线程执行，所以ART的做法为

\```
① entrypoint 改成 deoptimization entry
② 给所有线程挂"需要 deopt 这个方法的栈帧"的标记
③ 各线程在下一次安全检查点（checkpoint）自己处理：
   - 把编译帧的寄存器/局部变量/操作数栈 搬进新建的解释器帧
   - 这个过程叫 frame materialization（栈帧实体化）
   - 搬完 PC 指向解释器入口，继续跑
④ 对不在栈上的方法：不需要迁移，只作废代码即可
\```

deopt干的事情？
编译态下，调用方机器码可能是这样的

\```
; 调用 foo()
bl   0x7f12345678        ← 硬编码跳目标机器码
; 或者
ldr  x8, [x0, #offset]   ← 从 vtable 取 ArtMethod
ldr  x8, [x8, #entry_off]
blr  x8
\```

deopt做的就是让第一种形式失效

1. 目标方法的编译代码**作废**（不再被任何调用点信任）
2. 调用方原有的 `bl <旧地址>` 变成了无效跳转源
3. ART 重新解析调用 → 退回"每次读 entrypoint"的路径
4. 而 entrypoint 现在是 deopt entry / interpreter entry
所以简单来说deopt就是让两件事发生:
1.向下:目标方法自己的执行状态退回解释器
2.向上:所有指向它的调用点作废
我们frida的原理是把entrypoint换为自己的代码，这就出现了问题

| 方法状态 | 调用是否经过 entrypoint | hook 是否生效 |
|-|-|-|
| 解释执行 | 每次都读 | 生效 |
| 编译 + 调用点被内联/直接跳转 | 不读 | **失效** |
| deopt 后 | 每次都读（入口已是 trampoline） | 生效 |

\```
Java.deopt();                                                     // 清 JIT 缓存
Java.deoptimizeMethod("com.lptiyu.tanke.utils.u0",
                      "onLocationChanged",
                      "(Lcom/amap/api/location/AMapLocation;)V"); // 单方法降级
\```

所以我们可以通过单方法降级让hook生效

现在我们就确定了整个定位的流程

\```
系统 LocationManager.requestLocationUpdates("gps"/"network")
  → 高德定位SDK  com.amap.api.col.3sl.u5$c.onLocationChanged      (GpsLocation.java)
  → com.amap.api.location.AMapLocation.<init>                     ← 从 android.location.Location 复制
  → com.lptiyu.tanke.utils.u0.onLocationChanged(AMapLocation)     ← App 定位入口
  → com.lptiyu.tanke.activities.school_run.RunHelper.s0(AMapLocation)  ← 距离/配速消费点
\```

### 网络定位轨迹覆盖

什么是lbs，这不是系统的network provider

| 标记 | 是谁 | 数据怎么来 |
|-|-|-|
| `prov=gps` | 系统 gps provider | GNSS 硬件（我们已用 test provider 替换） |
| `prov=network` | 系统 network provider | 系统的基站/WiFi 粗定位 |
| **`prov=lbs`** | **高德自己的定位服务** | 采集 WiFi 列表 + 基站 → **上传高德服务器**（`apilocate.amap.com`）→ 服务器查指纹库返回坐标 |

`lbs` = Location Based Service。这是一条**完全独立于系统定位的通道** —— 高德自己发 HTTP 请求去查自己的数据库。
这个通道的输入是物理环节的指纹，周围有哪些wifi，哪个基站，输出是服务器数据库里面匹配到的参考点坐标

1. **App 配置了 `Hight_Accuracy`（高精度混合模式）**
2. 高德 SDK 内部多源竞争：GPS + 网络定位（lbs）+ 基站 + WiFi
3. 网络定位**先返回**（几十毫秒），GPS 在室内根本没有 fix,于是网络定位的结果被采用
4. 网络定位的结果是**服务器计算出来的**，基于 WiFi/基站指纹 → 设备不动 = 指纹不变 = 坐标恒定，所以距离一直为0

高德的libs定位:

1. 采集 WiFi 列表 + 基站信息
2. 上传到高德服务器（`apilocate.amap.com`）
3. 服务器查数据库返回坐标
4. 这个坐标精度通常 30-100+ 米
但是既然我们都模拟定位了，那肯定大概率在室内啊，所以信号不好
然后高德的选择为:gps不够，网络定位来凑
但是这个对我们并不友好，因为网络定位输入的是物理环境的指纹，我们伪造不了

### 高德拒绝provider

高德拒绝 test provider（errorCode=15）t
estprovider是系统的locationmanager允许测试提供者
一旦注册，所有监听 `gps` 的 App 收到的不再是真实 GNSS 数据，而是我们用 `set-test-provider-location` 塞进去的坐标。
**但它有个先天限制**：产出的每个 `Location` 都会被盖上 `mock` 标记。

但是注入后，虽然`Location.getLatitude` hook 读到了我们设的坐标，但是APP上面显示的距离不动
这说明我们的数据传入了应该传入的地方，但是不被接收

这里有个很重要的点：`u0` 收到的是 `AMapLocation`（高德自己的对象），不是原始 `Location`。所以 `err=15` 是**高德生成的**，不是系统给的。

系统的 Location 没有 errorCode 概念（`Location` 没有 errorCode 字段，它是 `AMapLocation` 才有的）。

所以这表示系统的location没问题，但是经过高德sdk处理后，报错了，当时传递出去的定位带有mock标志，怀疑是因为带有这个标志不行，于是通过Hook屏幕java mock getter

\```
L.isFromMockProvider.impl = () => false
L.isMock.impl = () => false
AL.isMock.impl = () => false
\```

把 Location.isFromMockProvider()（旧版）和 isMock()（Android 12+，含 LocationManager/Location 的多个重载）的实现直接替换成恒返回 false。

所以证明高德的判定不读取这三个java的getter

然后我们hook setmock函数，发现从没有命中，这证明:
系统给 test provider 的 Location 打 mock 标记，不走 `Location.setMock()`。
那是如何打的呢？在安卓源码中，

- `LocationManagerService` 在 test provider 场景下，调用 `Location.setMock(true)` 或者直接构造时设字段
- 实际上 AOSP 里 `LocationResult.setMock()` → 或者 `Location` 的构造函数带 mock 参数
在 Android 12+，`Location` 有个 `mIsMock` 字段，由 `LocationManagerService`/`TestProvider` 设置。
`Location.setMock(boolean)` 是 public API，但系统内部可能直接改字段。
**实测证明不走 public setMock，所以要么内部直改字段，要么在新版本换了 API。**

### 多源通道融合

通过上面可以发现有很多定位的渠道，但是高德是多源并存，然后给每个通道评分，谁的分高用谁

| 源 | provider | type | 特点 |
|-|-|-|-|
| GPS | `gps` | 1 | 精度高、室内无 fix |
| 系统网络 | `network` | — | 基站/WiFi 粗定位 |
| 高德服务器 | `lbs` | 2 | WiFi 指纹查库，**坐标恒定** |

那么这个是如何判断谁的分数高呢？先到先用然后本地质量过滤
需要注意的是以下几点:
1.没有全局融合器，GPS结果和LBS结果都各自独立，谁先完成谁先交付
2.竞争不在通道之间，而是每个通道自己的过滤阈值里面
3.上面的案例之所以采用LBS的方案是因为LBS恒定且能通过自身的弱过滤，但是gps被发现了mock被过滤掉了
