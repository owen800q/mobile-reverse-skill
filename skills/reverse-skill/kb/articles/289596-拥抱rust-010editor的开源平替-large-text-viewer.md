# 和 010editor的性能对比

010 搜几百MB的小文件基本秒出，但搜几个GB的大文件就会变得比较慢，读取时也不能秒开。调整了最大memory cache性能也没什么改变。相对的, large-text-viewer 的性能表现算的上很惊艳了

我的测试基准：

8GB 的trace 文件，每次用不同的关键词，搜索4次，看下耗时

 ![image](https://bbs.kanxue.com/upload/attach/202512/991803_TESDZMCFN97YDNK.webp)

010editor 第一次检索 8GB的 trace 用了十多秒，即使考虑到冷启动问题，每次搜索也都要等10秒多；哪怕刚搜过的关键词删除掉再搜索，这个时间也不会减少

 ![image](https://bbs.kanxue.com/upload/attach/202512/991803_8ZZN7HUVRWRGA59.webp)

而 large-text-viewer 打开文件秒开，只是在第一次搜索冷启动时略慢，然后在一定时间内搜索的速度会越搜越快，8个GB的trace文件，搜完几秒出，（测试时每次使用了不同的关键词）

# 原理分析

rust 想必大家都会读，话不多说，看看源码，查找大文件为什么这么快

项目分为 large-text-viewer 和 large-text-core, 前后端逻辑分离

前端使用了 rust 的即时渲染引擎 egui 来保证快速刷新，耗时的搜索和 io 则交给后端处理。中间通过异步消息通信

后端主要分为 4 部分

- FileReader：通过 memmap2 管理内存映射文件访问，一次性把文件映射到虚拟空间，负责提供底层io的接口
- LineIndexer：负责将行号映射到字节偏移量。它实现了混合索引策略，以平衡内存使用和访问速度。
- SearchEngine：一个并行化的搜索模块，可将内存映射文件分块扫描。
- Replacer ：处理文件修改，通过写时复制机制确保数据完整性。

# 动手改代码

# 动手改造

Q: 为什么010打开几GB的大文件需要加载一会

A: 为了把文本正确地按行展示，需要获取搜索整个文件中所有行起始符所在的偏移，并保存为index文件。这需要对文件进行一次遍历，是耗时操作。文本中的字节数据都是以byte形式存在内存中的，访问的时候是通过偏移来取，所以这个过程是在做快速映射

How: 怎么改进，large text viewer 原本的repo中对大于10mb的文本采用估算的方法: 取很行字符长度的平均值来估计行号，所以在大文件上容易出现行误差，本来应该是七千多万行，却发现估算值只有五千多万行。改进的方式大概有几种:

- 通过硬件加速，矢量化对齐等方式来强行减少遍历时间；
- 懒加载，先打开文件开头的部分，然后在后台线程完成遍历；
- 保留index文件，如果文件没被更改过，下次直接打开，无需加载；
