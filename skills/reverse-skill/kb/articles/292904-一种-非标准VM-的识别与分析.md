# 什么是"非标准 VM"

提到 VM 保护，多数人的第一反应是 VMProtect/自研栈管理/通用虚拟指令集/虚拟上下文。但现实中还存在另一条技术路线——把一段专用的数据处理逻辑（解密、解压、解析）改写成"字节码 + 解释器"的形式，仅凭一个固定循环驱动。这类 VM 不做通用计算，控制流几乎是一条直线，语义全部藏在数据流里。

我们暂时管这种类型叫做非标准 VM。它与标准 VM 的差异如下：

| **维度** | **标准 VM（VMP/栈机）** | **非标准 VM（以此样本为例）** |
|-|-|-|
| 计算模型 | 多用途计算 | 单用途（流密码解密） |
| 控制流 | 条件/间接跳转指令 | 无任意控制流转移指令 |
| 寄存器 | 虚拟寄存器，语义统一 | 槽混合状态表（指针/计数器/密钥/数据不分） |
| 指令格式 | 定长 opcode+操作数 | 32 位打包字，位域编码 |
| 分发 | 一般单级跳转表 | 两级分发（w15 大类 → w10 子操作码） |
| 内存 | 虚拟栈/虚拟堆 | 直接读写真实内存（ldrb 解引用宿主指针） |
| 指令实现 | ADD/SUB/MUL/XOR… | 移位/位运算/加减/比较/控制/条件拷贝 |

本文的目标函数是 sub_522E8：一个 0x6D60 字节（约 28KB）的巨型函数，样本本身带花指令与 CFF 混淆（篇幅所限不展开去混淆过程）。于是分析结合到动态侧：用 unidbg 跑出全量指令级 trace，从数据中找结构。

## 证据二：与数据无关的固定解码前导

\```

0x40052408: "str w9, [sp, #0x5c]"

这 17 条移位是无条件、恒定移位量的——不对数据做任何判断，只是机械拆包。这正是"指令解码器"的形态：与数据无关、每次都执行、输出喂给后续逻辑。

**判定结论与"回绕"机制**

四条证据合起来：固定取指循环→ 恒定解码前导→ 两级分发→ 共享寄存器文件。这是一个 VM，且控制流近似直线——但并非完全没有循环。

\```
0x40058148: ldr x8, [x6]             ; 取指指针
0x4005814C: add x0, x8, #4           ; 前移
0x40058150: str x0, [x6]
0x40058154: ldur x8, [x27, #-0x20]   ; 读循环状态
0x40058158: cmp x8, #2
0x4005815C: b.ge 0x4005816C          ; ≥2 走 0x5816C
0x40058160: cmp x8, #1
0x40058164: b.eq 0x40058178          ; ==1 → 回绕（死路径, 从未命中）
0x40058168: b 0x400581F0             ; ==0 → 正常路径
-- 0x4005816C: b.eq #0x400523A0      ; ==2 → 直接跳 0x523A0（快速继续）
-- 0x40058170: cmp x8, #3
0x40058174: b.ne 0x400581F0          ; >3 → 正常路径
-- 0x40058178（状态1/3 → 回绕路径）:
0x40058178: stur xzr, [x27, #-0x20]  ; 状态清零
0x40058180: ldur x0, [x27, #-0x18]   ; x0 = 回绕目标（由字节码预先写入）
0x4005819C: madd w8, w8, w8, w10     ; (473²+1) vs (219²·8-219²) —— 永远不等的假比较
0x400581AC: cmp w8, w9               ;   （反篡改垃圾代码, 恒走 b.ne）
0x400581EC: str x0, [x6]             ; 取指指针 = 回绕目标
-- 0x400581F0（正常/回绕两条路径汇合）:
0x400581F0: movz w8, #0x5e5          ; 魔数自检 0x5e5 != 0x9e5
0x400581fc: cmp w8, #0x9e5
0x40058200: b.ne #0x40052394         ; 回主循环进行边界检查
0x40052394: ldr x8, [sp, #0x20]
0x40052398: cmp x0, x8
0x4005239c: b.eq #0x40057f38
...
\```

三种状态在主循环入口的差异

状态0：0x58168 → 0x581F0 魔数检查 → 0x52394，走完整入口，先查第一边界 `cmp x0,[sp+0x20]`（相等则从 0x57F38 退出），再查第二边界 `cmp x0,[sp+0x28]`（相等则从 0x5902C 退出），还有 `cbz x0` 空指针检查，出现次数最多，应该是普通顺序执行。

状态2：0x5816C → 0x523A0，跳过第一边界检查（[sp+0x20] 终点判断），只查第二边界与空指针，回绕前过渡迭代的快速路径。

状态3：0x58178 回绕路径 → 0x581F0 魔数检查 → 0x52394，指针已被 0x581EC 改写为回绕目标，从目标地址重新取指，循环回绕。

字节码里没有任意跳转指令。它只有一种受控的循环原语——字节码先把"回绕目标"写进 [x27-0x18]、把"循环状态"写进 [x27-0x20]，解释器尾部按状态决定继续还是回绕，就是说：数据流携带条件性，控制流不携带语义。打个比方：标准程序像有岔道的铁路，火车走哪条道岔就是程序的意思；这个 VM 像一条环形传送带，轨道永远是那一圈，工人（handler）往工件（表里的值）上贴标签，传送带尽头的固定闸门（循环尾部）看一眼标签，决定"再转一圈"还是"放出去"。轨道从不变，货物决定一切。这与标准 VM"用跳转指令实现程序逻辑"的思路截然不同，也就是为什么静态分析无法识别这个VM的原因。

连续字节码解析

首字节计算用到的操作码

![image](https://bbs.kanxue.com/upload/attach/202609/887351_RYQYKEDR48DZAKQ.webp)

操作码解析

\```
一级分发  二级分发      语义                                   解析
0x11       无          数据内存取值                table[7] = data[0x298]=0x7d
0x35       0xd         条件计算                    table[1] = table[0x17] < table[0x12] ? 1: 0 = 1
0x27	   无          条件判断与回绕准备          根据table[1],写回绕目标与状态值
0x19       无          加常数                      table[2] = 0,计算后续要用到的偏移值
0x2f       无          数据内存取值                table[1] = data[0x6f0] = 0x4066db40,取密文地址
0x35       0x13        add64                       table[1] = table[1] + table[2],计算密文取址偏移地址
0x3e       无          ldrb                        table[3] = *table[1] = *0x4066db40 = 0x5
0x35       0x20        eor                         table[3] = table[3] ^ table[8] = 0x78
0x33       无          输出                        *table[1] = *0x4066db40 = table[3] = 0x78
\```

整张表拼起来就是一句话：这是一个 XOR 流密码解密器。

每轮流程：LDRB 读入 table[7] → 取密文基址 → 加偏移定位密文字节 → 装配密钥流指针 → LDRB 读密钥流字节 → EOR → 输出。

# 总结

当混淆方放弃通用 VM 而改用"近似直线、数据驱动"的专用解释器时，传统的"找跳转表"套路会完全失效；但 trace 里的取指循环、解码前导、分发统计和状态表还是可以找到分析的特征。
