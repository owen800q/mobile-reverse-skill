最近在根据[龙哥的文章](https://www.yuque.com/lilac-2hqvv/lfssh8/kd4pw2#qmshA)开发 unidbg 反检测时，遇到了内存地址截断的问题。由于 unidbg 采用经典的内存加载模型，与 64 位设备的 48 位虚拟空间差异很大，因此可以被作为检测点。

其中一种绕过的思路就是把`STACK_BASE` 和 `MMAP_BASE`抬高。他们在 unidbg 源码的 `unidbg-api/src/main/java/com/github/unidbg/memory/Memory.java` 中有定义。于是我试着将两个基址分别抬高到 `0x7f00000000L` 和 `0x7200000000L`（模拟真实设备的一些基址），结果遇到了以下错误：

![image](https://bbs.kanxue.com/upload/attach/202508/963087_R9TD4UPGA3J8UPF.png)

## 问题分析过程

### 第一次踩坑：地址范围限制

我尝试了多组 `MMAP_BASE` 地址进行测试：

- 原始地址：`0x40000000`
- 测试地址：`0x50000000`、`0x60000000`、`0x70000000` - 都能正常运行
- 问题地址：`0x80000000` 开始就失败

这个错误很奇怪，目标程序尝试读取 `0xb2000` 地址，但进程的 maps 中并没有对这个地址进行内存映射。一开始以为是内存地址冲突，但重新回顾内存布局后感觉不太可能。这更像是高位被截断了。

### 深入调试：定位问题根源

通过 trace 搜索 `0xb2000`，找到了问题的关键：

![image](https://bbs.kanxue.com/upload/attach/202508/963087_4G87VEVSVWY62W9.png)

在 IDA 中定位后发现，JNI 调用完的返回值就是 `0xb2000`。由于 unidbg 是自己处理 JNI 调用的，说明问题出在 unidbg 对 `GetStringUTFChars` 的处理上。

进一步调试发现，问题出现在 `pointer.toIntPeer()` 上：

![image](https://bbs.kanxue.com/upload/attach/202508/963087_MANA88JES8X78EQ.png)

`toIntPeer` 将 pointer 进行截断，使其符合 int 类型的范围。

### 理解 JNI 引用机制

翻阅源码得知，unidbg 使用三个 map 来处理 JNI 引用：

- `localObjectMap`
- `globalObjectMap`
- `weakGlobalObjectMap`

这些 map 将 JNI 引用对象的 hashcode 作为键，JNI 引用对象作为值。unidbg 可以通过以下代码取出一个 JNI 引用：

![image](https://bbs.kanxue.com/upload/attach/202508/963087_WTY83FVWS2JEAX2.png)

当时也是陷入了第二个错误的思路，误以为处理 JNI 引用的 map 中的键是一个内存地址（因为在真实设备的 demo 中，返回的值是一个堆地址）。

![image](https://bbs.kanxue.com/upload/attach/202508/963087_FERTCWAHP96UD49.png)

为了更好地解决问题，这里重新梳理了一下基础知识点

## 关键 JNI 函数分析

### `GetStringUTFChars`

用于字符串转换：`jstring → const char*`

**在 unidbg 中：**

1. 先从 jstring 提取出字符串的字节流
2. 通过 mmap（`com.github.unidbg.spi.AbstractLoader#allocateMapAddress`）开辟新空间存放新的内存块
3. 将字符串写入块中
4. 返回地址

**而在真实设备中：**

1. 从 JVM 内部获取一个字符串
2. JVM 内部会分配一块新的内存，用于存储源字符串的拷贝，以便本地代码访问和修改
3. 最后返回字符串的指针

### `FindClass`

给定输入类的字符串，返回一个 jclass 类型。

**对于 unidbg 来说，**返回的是一个 int 类型的哈希 hash。hash 由字符串调用哈希函数得来。

![image](https://bbs.kanxue.com/upload/attach/202508/963087_CYRW2YMTN96V4CY.png)

**对于真实设备来说，**返回的是一个类对象引用，一个指向 JVM 内部类元数据结构的指针，可以用它来查找方法、字段，或者用于反射等操作。

### `GetMethodID`

返回一个方法的标识符号，类型为 jmethodID。本质上是 JVM 内部用于定位某个方法的”句柄”或”索引”，**但它不是一个 Java 对象引用，也不是指向方法实现的 C 函数指针，不能用它做对象操作。**

**对于 unidbg 来说：**
返回的也是一个 int 类型的哈希 hash。

![image](https://bbs.kanxue.com/upload/attach/202508/963087_6KKBK4TQV8W82CH.png)

### unidbg 查询机制

- `com.github.unidbg.linux.android.dvm.DvmClass` 实现了类的处理，使用 `staticMethodMap`、`methodMap`、`fieldMap`、`staticFieldMap`、`nativesMap` 来查值，键为 hashcode
- `com.github.unidbg.linux.android.dvm.BaseVM` 中实现了对于 BaseVM 的类查询和对象查询，使用 `globalObjectMap`、`weakGlobalObjectMap`、`localObjectMap`、`classMap` 来查值，键也是 hashcode

## 问题根源与解决方案

**问题根源：**
unidbg 中，`GetStringUTFChars` 返回的是 mmap 申请内存的指针，又被 `toIntPeer()` 进行截断，所以导致返回值为 `0xb2000`，而这段地址未分配任何的内存映射，最终导致读取失败，引发错误。

而在真实设备中，`GetStringUTFChars` 返回的是 JVM 分配的字符串指针，所以指针在堆上，这也是为什么返回值被抬到很高的位置。

**解决方案：**
重新给出正确的地址就好了，也就是将 `return pointer.toIntPeer()` 改为 `return pointer.peer`。同样地，`GetStringChars` 的返回值也进行相应修改。

## 最终效果

修改后样本成功跑通

![image](https://bbs.kanxue.com/upload/attach/202508/963087_4BYQQ2A2XWR8WDX.png)

unidbg的代码还是写的挺棒的，借助这次的排错记录也是对JNI和unidbg的实现有了新的理解和认识，非常值得源码分析分析O(∩_∩)O
