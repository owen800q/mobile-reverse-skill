# Frida 常见检测与绕过

# 一、文件与进程名检测

这是最基础也是最常见的检测手段。由于绝大多数 Frida 教程都指导用户将服务端文件命名为 `frida-server` 并放置在 `/data/local/tmp/` 目录下，App 的防护机制会针对这些“标准特征”进行扫描。

## 1. 检测原理

防护代码通常会在 App 启动时执行以下检查：

### (1) 文件特征扫描

App 会尝试访问 Android 系统中的常见临时目录，查找是否存在包含 `frida` 关键字的文件。

- **扫描路径**：`/data/local/tmp/` (最常用), `/data/local/`, `/sdcard/`
- **敏感文件名**：`frida-server`, `frida-agent`, `re.frida.server`

**代码示例** **(伪代码)** ：

| 12345 | `File file =` `new` `File(``"/data/local/tmp/frida-server"``);``if` `(file.exists()) {``// 发现 Frida，触发闪退或上报``killApp();``}` |
|-|-|

### (2) 进程名扫描

App 可以通过 Shell 命令或读取系统文件来获取当前运行的所有进程列表，并匹配黑名单。

- **扫描方式**：执行 `ps -A` 查看进程状态。

![image](https://bbs.kanxue.com/upload/attach/202512/1036360_NS33WXWSMXR4P66.png)
- **敏感关键字**：`frida-server`, `frida-helper`, `frida-launcher`

**代码示例 (伪代码)** ：

| 12345678910 | `// 读取 /proc/[pid]/cmdline 或执行 ps 命令``Process process = Runtime.getRuntime().exec(``"ps -A"``);``BufferedReader reader =` `new` `BufferedReader(``new` `InputStreamReader(process.getInputStream()));``String line;``while` `((line = reader.readLine()) !=` `null``) {``if` `(line.contains(``"frida-server"``)) {``// 发现 Frida 进程``throw` `new` `RuntimeException(``"Frida detected!"``);``}``}` |
|-|-|

---

## 2. 绕过方案

针对上述特征检测，最直接有效的方法就是 **“改名”** 。

### 方案一：重命名 Frida 服务端 (推荐)

这是最简单的一步。将 `frida-server` 重命名为类似系统进程的名字，既能避开文件扫描，启动后的进程名也会随之改变，从而避开进程扫描。

**操作步骤**：

| 123456789101112 | `# 1. 停止当前运行的 frida-server``pkill -f frida-server` `# 2. 进入目录``cd` `/data/local/tmp` `# 3. 重命名 (例如改为 fs 或 system_server_custom)``mv` `frida-server-16.x.x-android-arm64 fs` `# 4. 运行``chmod` `+x fs``.``/fs` `&` |
|-|-|

### 方案二：使用 HLuda (去特征版 Frida)

有些深度检测不仅仅匹配文件名，还会扫描二进制文件内部的字符串特征（如 `frida:rpc` 字符串）。
此时，单纯重命名文件无效。你需要使用 **HLuda**（魔改版 Frida）。

- **原理**：HLuda 在编译阶段修改了源码中的所有 `frida`、`gum`、`gmain` 等敏感字符串关键字。
- **效果**：彻底去除二进制层面的字符串特征。

# 二、监听端口检测

Frida 在运行时需要开启 TCP 端口与电脑端进行数据传输。如果不加配置，Frida 会默认绑定特定的特征端口，这成为了 App 检测的重要依据。

## 1. 检测原理

Frida 服务端启动后，默认会监听以下两个端口：

- **27042**：主控制端口 (control connection)
- **27043**：辅助通信端口 (cluster connection)

防护代码通常采用以下方式进行探测：

### (1) 扫描系统网络连接 (netstat)

App 可以执行 `netstat` 命令，查看当前系统是否有名为 `0.0.0.0:27042` 或 `127.0.0.1:27042` 的监听状态。

\```
netstat -tuln | grep 27042
\```

![image](https://bbs.kanxue.com/upload/attach/202512/1036360_XFX9UM6U4QX7GQV.png)

---

## 2. 绕过方案

绕过的核心思想是  **“避开默认”** 。只要我们不使用 27042 端口，上述针对固定端口的扫描就会失效。

### 步骤一：指定非标准端口启动

在手机端启动 `frida-server` 时，使用 `-l` (listen) 参数指定一个随机的非标准端口（例如 `8888` 或 `6666`）。

| 123 | `# 格式：./frida-server -l 地址:端口``# 0.0.0.0 表示允许任何接口连接（包括 USB 和 WiFi）``.``/frida-server` `-l 0.0.0.0:8888 &` |
|-|-|

### 步骤二：配置电脑端连接

修改端口后，电脑端的 Frida 客户端不会自动识别，必须手动进行端口转发或指定连接地址。

**方式 A：通过 USB 转发 (推荐)**
我们需要将电脑的 `8888` 端口转发到手机的 `8888` 端口。

| 12345 | `# 1. 设置转发``adb forward tcp:8888 tcp:8888` `# 2. 连接 (此时客户端可以像往常一样使用 -U 或 -R，或者指定 -H)``frida -H 127.0.0.1:8888 -l hook.js -f com.example.target` |
|-|-|

**方式 B：通过 WiFi 连接**
如果手机和电脑在同一局域网，可以直接指定手机 IP。

| 12 | `# 假设手机 IP 为 192.168.1.10``frida -H 192.168.1.10:8888 -l hook.js -f com.example.target` |

# 三、ptrace 占坑 (双重附加检测)

这是 Android Native 层反调试最经典的手段之一。

## 1. 检测原理 (独占性原则)

Linux/Android 内核规定：**同一个进程同时只能被一个调试器（Tracer）附加**。

- **Frida 的工作原理**：Frida 本质上也是一个调试器，它需要通过 `ptrace` 系统调用附加（Attach）到目标 App 进程上才能进行 Hook。
- **App 的防御手段**：App 在启动的极早期（通常在 `.init_array` 或 `JNI_OnLoad` 中），主动调用 `ptrace(PTRACE_TRACEME, 0, 0, 0)` 自己附加自己。
- **冲突结果**：

	- 如果 App 先抢占了 `ptrace` 位置，Frida 再尝试 Attach 时，系统会返回 `EBUSY` 错误，导致注入失败。
	- 反之，如果 Frida 已经附加，App 再调用 `ptrace` 会失败。App 检测到失败返回值（-1）后，就知道自己正在被调试，从而选择闪退或自杀。

**代码示例 (C/C++)** ：

| 123456 | `// 简单的反调试逻辑``int` `status = ptrace(PTRACE_TRACEME, 0, 0, 0);``if` `(status == -1) {``// ptrace 失败，说明已经被别人（如 Frida/IDA）附加了``kill(getpid(), SIGKILL);` `// 自杀``}` |
|-|-|

---

## 2. 绕过方案

针对 `ptrace` 占坑，单纯的“Attach 模式”是必死的。我们需要利用 Frida 的 **Spawn 模式** 抢在 App 运行代码前介入，并**修改** App 的检测逻辑。

### 步骤一：使用 Spawn 模式 (冷启动)

Spawn 模式 (`-f`) 会由 Zygote 进程 fork 出目标 App，并在 App 执行任何自己的代码（包括反调试代码）之前将 Frida 的 Gadget/Agent 注入进去。

这给了我们一个“时间差”：Frida 先进去了，现在轮到 Frida 掌控局面。

### 步骤二：Hook 并不再调用原 ptrace

仅仅进入是不够的。如果 Frida 保持附加状态，App 随后的 `ptrace` 调用会失败，App 依然会发现并退出。
**根本的解决办法是**：Hook `libc.so` 中的 `ptrace` 函数，拦截 App 的调用，直接返回 0（假装成功），并且**不要**执行真正的 `ptrace` 系统调用。

**示例脚本**：

| 123456789101112131415161718192021222324252627282930 | `function` `bypassPtrace() {``var` `ptracePtr = Module.findExportByName(``"libc.so"``,` `"ptrace"``);` `if` `(ptracePtr) {``// 使用 Interceptor.replace 完全替换掉 ptrace 的实现``Interceptor.replace(ptracePtr,` `new` `NativeCallback(``function``(request, pid, addr, data) {``console.log(``"[+] ptrace called - bypassing..."``);``console.log(``"    request: "` `+ request);` `// PTRACE_TRACEME 的常量值通常是 0``if` `(request == 0) {``console.log(``"    [+] Blocked PTRACE_TRACEME!"``);``// 直接返回 0，欺骗 App 说“你已经成功附加自己了”``return` `0;` `}` `// 如果有其他 ptrace 需求，可以在这里放行，或者全部屏蔽``return` `0;`  `},` `'long'``, [``'int'``,` `'int'``,` `'pointer'``,` `'pointer'``]));` `console.log(``"[+] ptrace bypass applied!"``);``}` `else` `{``console.log(``"[-] ptrace not found"``);``}``}` `setImmediate(``function``() {``bypassPtrace();``});` |

# 四、D-Bus 协议通信检测

Frida 的客户端与服务端通信基于 **D-Bus** 协议（一种进程间通信/RPC 机制）。即使我们将 Frida 服务端改名并迁移目录，其通信协议的特征（尤其是握手阶段）依然是固定的。

## 1. 检测原理

App 可以遍历本地所有开放的 TCP 端口，并尝试建立 Socket 连接。一旦连接成功，App 会发送 D-Bus 协议特定的握手消息。如果服务端响应了特定的 D-Bus 关键字（如 `REJECT`），则可认定该端口运行着 Frida。

### 检测逻辑流程：

1. **遍历端口**：扫描 `/proc/net/tcp` 找到所有开放端口。
2. **建立连接**：尝试 Socket Connect。
3. **发送探测包**：发送 D-Bus 认证字节（通常是 `\0` 或 `AUTH`）。
4. **特征匹配**：Frida 服务端（frida-server）在收到未认证的握手请求时，通常会按照 D-Bus 标准回复 **`REJECT`** 开头的信息。App 收到 `REJECT` 即判定检测成功。
5. **内存扫描**：同时，App 可能会扫描内存映射，查找 `frida:rpc`、`gmain` 等 D-Bus 相关字符串。

**检测代码示例 (伪代码)** ：

| 12345678910111213141516 | `Socket socket =` `new` `Socket(``"127.0.0.1"``, port);``InputStream is = socket.getInputStream();``OutputStream os = socket.getOutputStream();` `// 发送 D-Bus 握手空字节``os.write(``new` `byte``[]{``0``});`  `// 读取响应``byte``[] buffer =` `new` `byte``[``512``];``int` `len = is.read(buffer);``String response =` `new` `String(buffer,` `0``, len);` `// 检测 REJECT 关键字``if` `(response.contains(``"REJECT"``)) {``// 发现 Frida！``}` |
|-|-|

---

## 2. 绕过方案

### 方法一：Hook 字符串比较函数 (动态拦截)

这是您提到的方法。原理是拦截 App 在处理网络响应时的比较逻辑。当 App 拿收到的数据去匹配 "REJECT" 时，我们欺骗它说“没匹配上”。

注意：`strcmp` 和 `strstr` 是系统底层极其高频调用的函数。直接 Hook 会导致 App 巨卡无比甚至崩溃，**必须加严格的过滤条件**。

| 12345678910111213141516171819202122232425262728 | `function` `bypassDBusDetection() {``var` `strstr = Module.findExportByName(``"libc.so"``,` `"strstr"``);` `if` `(strstr) {``Interceptor.attach(strstr, {``onEnter:` `function``(args) {``// args[0]: haystack (被搜索的字符串)``// args[1]: needle (要查找的关键词)` `this``.needle = Memory.readUtf8String(args[1]);` `// 只有当 App 正在查找敏感关键词时才介入``if` `(``this``.needle && (``this``.needle.indexOf(``"REJECT"``) !== -1 \|\|` `this``.needle.indexOf(``"frida"``) !== -1)) {``this``.detected =` `true``;``// console.log("[*] Detected suspicious strstr check: " + this.needle);``}``},``onLeave:` `function``(retval) {``if` `(``this``.detected) {``// 如果找到了 REJECT，强行返回 0 (NULL)，表示没找到``// 从而欺骗 App``retval.replace(0);``// console.log("[+] Bypassed D-Bus check!");``}``}``});``}``}` |
|-|-|

### 方法二：使用魔改版 Frida (HLuda) - **推荐**

相比于在运行时 Hook 极不稳定的 `strstr`，最彻底的办法是从源码层面消除特征。

**HLuda**（或其他去特征版本）在编译 Frida 时做了如下修改：

1. **修改协议关键字**：将源码中的 `REJECT` 替换为其他单词（如 `ACCESS`）。
2. **去除内存特征**：将 `frida:rpc` 替换为 `data:rpc` 等。

使用此类版本后，App 发送探测包收到的将不再是标准的 `REJECT`，从而直接绕过检测机制，无需编写任何 Hook 脚本。

# 五、检测 /proc/pid/fd (文件描述符)

在 Linux/Android 系统中，一切皆文件。`/proc/pid/fd/` 目录包含了当前进程打开的所有文件描述符（File Descriptors）。App 通过遍历该目录，可以获知进程加载了哪些文件、建立了哪些 Socket 连接。

## 1. 检测原理

### (1) 扫描逻辑

App 遍历 `/proc/self/fd` 目录下的所有文件，并使用 `readlink` 读取符号链接指向的**真实路径**。

- **相关命令**：`ls -l /proc/self/fd` 或 `readlink -f /proc/self/fd/<id>`
- **检测代码示例 (伪代码)** ：

| 12345678 | `File fdDir =` `new` `File(``"/proc/self/fd"``);``for` `(File fd : fdDir.listFiles()) {``// 读取软链接指向的路径``String realPath = Os.readlink(fd.getAbsolutePath());``if` `(realPath.contains(``"frida"``) \|\| realPath.contains(``"gum-js"``)) {``// 发现异常``}``}` |
|-|-|

### (2) 关键特征

如果 Frida 注入成功，该目录下可能会出现指向以下路径的链接：

- **传统特征 (旧版 Frida)** ：

	- `/data/local/tmp/frida-server`
	- `/data/local/tmp/frida-agent-64.so`
	- `/memfd:frida-agent` (无文件内存映射)
	- `/memfd:gum-js-loop`

>
> 在 **高版本 Frida (>=16)** 时：
>
>
> - 不再使用 memfd:frida-agent（换成匿名 tmpfs）
> - 不再暴露 frida-agent-xxx.so
> - eventfd 也与系统难以区分
> - 不再在 fd 中出现 Gum 的通信结构
>
>
> 检查 FD 已经基本无法检测 Frida。
>
>
> 在 **Android 10+** 中，Google 对 memfd 的名称做了更严格的匿名化，Frida 使用的 memfd **不再暴露名称**。
>
>
>

---

## 2. 绕过方案 (IO 重定向)

无论特征如何变化，检测的核心动作都是调用 `readlink` 或 `readlinkat` 系统函数。
**核心思路**：Hook 这两个函数，当 App 试图读取的文件描述符指向包含 `frida`、`gum` 或 `memfd` 的路径时，将其**替换**为合法的系统路径（如 `/dev/null` 或 `libc.so`）。

# 六、检测 /proc/pid/task 线程名

在 Android (Linux) 系统中，进程的每一个线程在 `/proc/pid/task/` 目录下都有一个对应的子目录（目录名为线程 ID）。

App 可以遍历该目录，读取每个线程的 **`status`** 或 **`comm`** 文件，获取线程名称。由于 Frida 依赖 GLib 库，运行时会创建特定的辅助线程，这些线程的默认名称具有极高的辨识度。

## 1. 检测原理

### (1) 关键文件

- `/proc/self/task/<tid>/comm` ：仅包含线程名（最常用，读取方便）。
- `/proc/self/task/<tid>/status` ：包含线程的详细信息，其中第一行 `Name: ...` 即为线程名。

### (2) 典型特征

如果 Frida 注入成功，进程中通常会出现以下命名的线程：

| 线程名 | 来源 | 说明 |
|-|-|-|
| **`gmain`** | GLib | Frida 基于 GLib 开发，这是 GLib 的主循环线程。 |
| **`gdbus`** | GLib | 用于 D-Bus 通信的线程。 |
| **`gum-js-loop`** | Frida | GumJS 引擎的 JavaScript 事件循环线程。 |
| **`pool-frida`** | Frida | Frida 的线程池（某些版本出现）。 |
| **`linjector`** | Injector | 某些注入工具留下的痕迹。 |

![image](https://bbs.kanxue.com/upload/attach/202512/1036360_25Y7VPUKVC3M69P.png)

## 2. 绕过方案

# 八、检测 Inline Hook (代码完整性校验)

Inline Hook 是 Frida `Interceptor` 模块的核心机制。它的原理是直接修改内存中目标函数的**前几条指令（Prologue）** ，将其替换为一条跳转指令（Trampoline/跳板），从而将程序执行流引导至 Frida 的处理函数。

## 1. 检测原理

App 可以通过检查关键函数开头的机器码（Machine Code）是否被篡改来检测 Hook。

### (1) 指令替换特征 (ARM64)

在 ARM64 架构下，Frida 通常需要替换前 16 个字节（4 条指令）来实现长跳转。它会将原始指令备份，并写入以下经典的 **"LDR + BR"** 跳板指令：

- **Hook 前 (原始指令)** ：
这是函数原本正常的汇编指令（示例）：

\```
# Hex: ff c3 04 d1 fd 7b 0e a9 fc 7b 00 f9 f8 5f 10 a9
sub sp, sp, #0x30      ; 申请栈空间
stp x29, x30, [sp, #0x20] ; 保存寄存器
str x28, [sp, #0x10]
str x24, [sp, #0x20]
\```
- **Hook 后 (Frida 特征)** ：
内存中的指令变成了跳转逻辑：

\```
# Hex: 50 00 00 58 00 02 1f d6 [Address 8 bytes]
ldr x16, #8            ; 0x58000050: 将当前 PC+8 处的地址加载到 X16 寄存器
br  x16                ; 0xd61f0200: 跳转到 X16 寄存器指向的地址 (Frida Stub)
.long 0x747d3e6e       ; 具体的跳转绝对地址 (低位)
.long 0x00000000       ; 具体的跳转绝对地址 (高位)
\```

### (2) 检测逻辑

App 会计算内存中函数前 N 个字节的 **CRC32** 或 **MD5** 值，并与本地文件（SO 库）中该函数的原始机器码进行比对。

- **如果不一致**：说明指令被篡改，存在 Inline Hook。
- **特征码扫描**：直接扫描内存开头是否包含 `50 00 00 58` (LDR X16, #8) 这类 Frida 惯用的跳转指令。

---

## 2. 绕过方案

### 方法一：Hook 比较函数 (memcmp)

检测逻辑的核心在于“比对”。App 通常会读取磁盘上的 SO 文件内容与内存内容进行比较。我们可以 Hook `libc.so` 中的 `memcmp` 函数。
当发现 App 正在比对我们已 Hook 的函数地址时，强行让 `memcmp` 返回 0（即相等），从而“指鹿为马”。

# 九、完整性校验 (CRC/MD5 检测)

Frida 的 Inline Hook 机制本质上是 **“篡改内存代码”** 。即使只修改了几个字节（写入跳转指令），也会导致该内存区域的校验和（Checksum）发生变化。

## 1. 检测原理

App 通常采用 **“磁盘 vs 内存”** 的比对方式来检测代码是否被篡改。

### (1) 校验逻辑

1. **基准值获取 (磁盘)** ：App 读取 APK 包内或 `/data/app/.../lib/` 目录下的原始 SO 文件 (`.text` 段)，计算其 CRC32 或 MD5 值。这是“正确”的值。
2. **当前值获取 (内存)** ：App 遍历当前进程的内存空间，找到该 SO 库的加载基址，读取对应内存段的机器码，计算当前的 CRC32 或 MD5 值。
3. **比对**：如果两个哈希值不一致，说明内存中的代码被修改过（存在 Hook）。

### (2) 触发场景

- **Inline Hook**：Frida 为了拦截函数，必须修改函数开头的指令（前 16 字节），这直接破坏了完整性。
- **软件断点**：调试器插入断点会写入 `0xCC` (INT 3) 指令，同样会改变 CRC。

**检测代码逻辑 (伪代码)** ：

## 2. 绕过方案

### 方案一：使用硬件断点 (无痕 Hook)

既然修改代码会被检测，那就不要修改代码。
Frida 提供了硬件断点功能（基于 CPU 的调试寄存器），可以在不修改内存字节的情况下实现拦截。

- **API**：`Process.setExceptionHandler(...)` 配合 `DebugSymbol`。
- **优点**：完美绕过 CRC/MD5 校验。
- **缺点**：硬件资源有限（ARM64 通常只有 4-6 个断点槽位），无法大规模 Hook。

### 方案二：Hook 校验函数 (指鹿为马)

找到 App 计算或比对 CRC 的核心函数（如 `memcmp`、自定义的 `check_crc`），对其进行 Hook。

- **思路**：当 App 比较 `libnative.so` 的代码段时，强行返回“相等”或“校验通过”。

### 方案三：Hook 文件读取 (IO 重定向)

如果 App 是通过 `open`/`read` 读取磁盘文件来计算基准值的，我们可以 Hook 这些 IO 函数。

- **思路**：当 App 试图读取磁盘上的 SO 文件时，我们将其重定向到内存中已经被 Hook 的那段数据上（或者反过来，当它读内存时给它返回磁盘数据）。

	- *注意*：这需要非常精细的操作，逻辑较复杂，通常不如方案一、二实用。
