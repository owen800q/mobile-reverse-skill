# 某海外电商app设备指纹收集与加密算法分析

最近好像比较流行用ai水文章，我也用ai水几篇。这份是用ai自动分析了某电商的设备指纹函数trace。将3GB的trace文件交给ai自动分析后的结果。

我只使用[QTrace](https://bbs.kanxue.com/thread-290574.htm)对关键的指纹收集函数做trace，然后将trace文件直接交给ai自动分析，其余的不做干预。总共分析了不到20分钟
![图片描述](https://bbs.kanxue.com/upload/attach/202610/872365_J63RKGH2TV3B44S.webp)
报告包含完整的指纹采集点，源码级实现逻辑，和数据加密方式。

## 报告说明

本报告中的结论分为三类：

1. **运行时直接观察**：来自 QBDI trace 中的 JNI、libc、字符串和内存操作。
2. **静态确认**：来自 `libriver.so` ARM64 反汇编，以及 APK 中 `ri.bg`、`s13.c` 等 Java 类反编译。
3. **未完整覆盖的上游输入**：trace 仅记录到最终值，但没有覆盖其 producer。源码通过 `AppInputs` 明确接入，绝不使用猜测逻辑冒充原实现。

所谓“源码级等价实现”，指在相同 Android 版本、相同应用 UID、相同私有数据、相同运行时 block list 和相同实时设备状态下，按 trace 观察到的 API、顺序、格式及编码方式重现采集。时间、随机数、内存、电池、网络、sequence 和密文按设计会随会话变化。

## 1. 样本与结论

- Trace：`D:\tomu\tomu_env_9.trace`，3,645,346,354 字节，QBDI ARM64 逐指令 trace。
- 对应 native 模块：`D:\tomu\tomu\split_config.arm64_v8a\lib\arm64-v8a\libriver.so`
- SHA-256：`2774ae72fd2c42a0857942a1fe187e46f807d4ee61dfe38dcdbbbbc81d297e08`
- trace 入口配置：`D:\tomu\tea_trace\nativelib\src\main\cpp\native_main.cpp:91`，`trace_func = 0x2604ac`。
- 最终明文是 URL query-string；加密结果是一个二进制信封，经标准 Base64 后包装为：

```json
{"encryptedData":"<standard-base64>"}
\```

本次实际结果：Base64 长 14,500，解码后 10,873 字节。

**加密算法链已经可以确定为：随机临时密钥材料 + 32 字节共享秘密派生 + SHA-256/HMAC/HKDF 类 KDF + ChaCha20-Poly1305 风格 AEAD 信封。** 最后一层的结构与长度关系完全吻合 `12-byte nonce + ciphertext + 16-byte tag`；加密数据不是 AES 分组密文（总长不是 16 的倍数）。

>
> 注意：该包高度控制流混淆，静态伪代码中的函数名均为本文按行为命名。算法流程和长度关系为高置信度；固定服务端公钥/协议常量仍应从当前版本运行时内存提取，而不能凭空写死。
>

## 3. 明文组装的准确逻辑

```cpp
string form_encode(const vector<pair<string,string>>& fields) {
    string out;
    for (size_t i = 0; i < fields.size(); ++i) {
        if (i) out += '&';
        out += url_encode(fields[i].first);  // 字段名本身通常无需变化
        out += '=';
        out += url_encode_utf8(fields[i].second); // 空格 -> '+'，其余按 %HH
    }
    return out;
}

string build_p_block() {
    // 必须保持 p1 ... p21 的原始顺序；空值仍输出 key=
    return form_encode({

        {"p2", collect_keystore_cert_chain()},
        {"p3", collect_first_boot_state()},

        {"p9", sim_operator_display()},
        {"p10", android_id_via_content_resolver_call()},
        {"p11", ""},
        {"p12", default_sms_package_record()},
        {"p13", display_record()},
        {"p14", installer_package_or_null()},
        {"p15", installer_environment_code()},
        {"p16", audio_stream_json()},
        {"p17", locale_language_country()},
        {"p18", timezone_id_and_name()},
        {"p19", power_profile_info()},
        {"p20", soc_model()},
        {"p21", settings_ad_aaid()}
    });

string build_plaintext() {
    vector<pair<string,string>> f;
    // 按 trace 中固定顺序 push version ... dme
    // 再 push platform_type ... bgid；空值不能省略。
    // 某些复杂子结构先自行用 |、;、, 拼接，再作为一个整体 URL 编码。
    return form_encode(f);

\```

这里最重要的是：**顺序固定、空字段保留、复杂字段先内部拼接后整体 URL 编码**。改变顺序或省略空字段会改变最终密文和服务端解释。

## 4. 加密信封

### 4.1 二进制布局

trace 显示明文加密前长度为 `0x2A1B = 10779` 字节；固定/AAD 头长度为 `0x52 = 82` 字节。最终长度：

\```
82 + 12 + 10779 + 16 = 10873
\```

与实际 Base64 解码后的 10,873 字节完全一致。因此布局为：

\```
offset  size                 含义
0       82                   protocol header / AAD
82      12                   AEAD nonce
94      plaintext_length     ciphertext（与明文等长）
94+N    16                   authentication tag
\```

`sub_2D9794`（`0x2D9794`）直接给出组包公式：

```cpp
out_len = plaintext_len + 16 + aad_len + 12;
out = new byte[out_len];
AEAD_encrypt(key32, plaintext, plaintext_len,
             aad82, 82, nonce12, ciphertext_and_tag);
memcpy(out, aad82, 82);
memcpy(out + 82, nonce12, 12);
memcpy(out + 94, ciphertext_and_tag, plaintext_len + 16);
\```

### 4.2 82 字节 header 的内部布局

`sub_2EBF5C`（`0x2EBF5C`）逐字节构造：

\```
0x00  2   协议版本/算法标记（两个固定字节）
0x02 32   临时公钥/公钥材料 A
0x22 32   随机 salt/公钥材料 B
0x42  8   64 位时间/随机数，按固定端序写入
0x4A  8   调用方传入的 64 位请求标识
总计 0x52 (82)
\```

对应伪代码：

```cpp
header[0] = PROTOCOL_BYTE_0;
header[1] = PROTOCOL_BYTE_1;
memcpy(header + 2,  ephemeral_public_or_material_A, 32);
memcpy(header + 34, random_salt_or_material_B,       32);
store_u64_protocol_endian(header + 66, generated_u64);
memcpy(header + 74, &request_id_u64, 8);
\```

### 4.3 密钥派生

`sub_2EBF5C` 的数据流：

1. `sub_EABBC(..., 32)` 从安全随机源生成 32 字节临时私钥/随机数；trace 同时观察到 `/dev/urandom`。
2. `sub_E0544` 从该 32 字节值计算 32 字节公钥材料。
3. `sub_E0D40` 用该临时私钥和调用方传入的 32 字节公钥计算 32 字节共享秘密。这组 32-byte 输入/输出及调用关系符合 X25519/ECDH 类交换。
4. 再生成 32 字节随机 salt。
5. `sub_2EC39C` → `sub_EA4AC` / `sub_EA7D4`，基于 SHA-256/HMAC 状态把共享秘密和 salt 派生成最终 32 字节 AEAD key，行为符合 HKDF-SHA256 的 extract/expand。

```cpp
uint8_t eph_private[32] = secure_random_32();
uint8_t eph_public[32]  = x25519_public(eph_private);
uint8_t shared[32]      = x25519(eph_private, server_public_key);
uint8_t salt[32]        = secure_random_32();
uint8_t key[32]         = hkdf_sha256(shared, salt, /*info=*/empty, 32);
\```

### 4.4 AEAD 及 Base64/JSON

```cpp
vector<uint8_t> encrypt_envelope(
    bytes plaintext,
    uint64_t request_id,
    bytes32 server_public_key)
{
    bytes32 sk   = secure_random_32();
    bytes32 pub  = x25519_public(sk);
    bytes32 salt = secure_random_32();
    bytes32 ss   = x25519(sk, server_public_key);
    bytes32 key  = hkdf_sha256(ss, salt, {}, 32);

    byte aad[82];
    aad[0] = PROTOCOL_BYTE_0;
    aad[1] = PROTOCOL_BYTE_1;
    memcpy(aad + 2, pub, 32);
    memcpy(aad + 34, salt, 32);
    store_u64_protocol_endian(aad + 66, generated_u64());
    memcpy(aad + 74, &request_id, 8);

    byte nonce[12] = secure_random_12();
    auto [ciphertext, tag16] = chacha20_poly1305_encrypt(
        key, nonce, plaintext, /*AAD=*/aad);

    return concat(aad, nonce, ciphertext, tag16);
}

string final_result =
    "{\"encryptedData\":\"" + base64_standard(envelope) + "\"}";
\```

`sub_150144` / `sub_14EAC0` 是标准 Base64 编码路径；trace 最终明确按 `"encryptedData":"` + Base64 + `"}` 组装。

## 6. 准确性边界

已由 trace **直接观察并确认**：字段名称、字段顺序、大部分字段值、JNI/系统 API、URL 编码后的两层明文、明文长度、82/12/16 字节结构、最终 Base64 和 JSON 包装。

由反汇编与长度关系**高置信度识别**：X25519/ECDH 类 32-byte 密钥交换、HKDF-SHA256 类派生、ChaCha20-Poly1305 风格 AEAD。

当前证据中不能负责任地写死：两个协议字节、服务端长期公钥、header 两个 32-byte 槽位的官方字段名，以及少数混淆字段（如 `p15`）的官方业务命名。它们随版本/会话变化，正确实现应从调用参数和运行时产生，而不是复制本次样本值。

## 为什么部分字段必须作为输入

“能编译”不等于“准确”。对 trace 没有执行到 producer 的字段，写一个看似合理的 Android API 会制造错误结论。因此源码把这些字段显式定义成 `AppInputs`：调用方必须接入原始 Tomu 模块或继续针对相应 producer 补 trace。这样已观察到的采集逻辑可以完全重现，而未知项不会被伪造。

# 复现工程使用与限制

## Files

- `EnvCollector.java`: source-level Java equivalents for every field whose producer is observable in `tomu_env_9.trace`.
- `../tomu_env_9_analysis.md`: field inventory, native encryption call graph and evidence notes.

The source was compiled successfully against Android API 37's `android.jar`.

## Usage

```java
EnvCollector.AppInputs appInputs = new EnvCollector.Defaults() {
    @Override public String uuid() { return loadTomuPersistedUuid(); }
    @Override public String u2() { return generateU2(); }
    @Override public String cookie() { return loadCookie(); }
    @Override public String p15() { return calculateP15(); }
    @Override public String didInfo() { return buildDidInfo(); }
};

String pBlock = EnvCollector.buildPBlock(context, appInputs);
String main = EnvCollector.buildMainQuery(context, appInputs);
String plaintext = EnvCollector.appendNativeFields(context, main, appInputs);
\```

`pBlock` is a separate collected block seen in the trace. Its placement inside the product's higher-level request is controlled by the caller. The final native plaintext in this trace is the `main` query followed by the native fields in `appendNativeFields`.

## Exactness boundary

A different application cannot completely reproduce Tomu's values merely by calling public Android APIs:

1. `tomu_secure_v2`, `se_config`, the UUID, cookie, `u2`, and related IDs are private to Tomu's UID/data directory.
2. Package visibility and hidden-API policy change the service/package/display results.
3. `ri.bg.cb(field)` can suppress individual `pN` fields using a runtime block list supplied elsewhere in the app.
4. `p3`, `p15`, `u2`, `cookie`, `did_info`, `rom_status`, `sequence`, `bgid`, and several obfuscated fields are supplied by other app/native subsystems. The trace contains their values but does not contain enough producer execution to reconstruct those producers accurately. They are explicit `AppInputs`, rather than fabricated implementations.
5. Time, memory, battery, storage, IP, random, sequence and cryptographic values are intentionally session-dependent.

For exact same-device reproduction, execute this code in the original app process/UID and provide the `AppInputs` from the original app modules. Otherwise, the methods reproduce collection semantics but values legitimately differ.

## Important corrected details

- `p12` signature hash is **MD5 of `Signature.toCharsString()` UTF-8 bytes**, uppercase hex. This follows APK class `ri.bg.dg -> s13.c.b`, not MD5 of raw certificate bytes.
- URL encoding uses Java `URLEncoder` behavior: UTF-8, space to `+`, percent encoding with uppercase hex.
- Empty fields are emitted.
- Field order is protocol-significant and represented explicitly in source.
- Battery extra order follows `Bundle.keySet().iterator()` exactly as observed; Android does not promise this order across versions.

    public static String collectP1ServiceProbe() {
        List<String> services = listServicesHidden();
        String[] suspects = {"oppo", "miui", "vivo", "meizu", "redmi", "xiaomi", "huawei",
                "oneplus", "lineage", "samsung", "xposed", ".leui.", "realme", "asus",
                "blackshark", "meitu", "libsu"};
        List<String> hits = new ArrayList<>();
        for (String service : services) {
            String lower = service.toLowerCase(Locale.ROOT);
            for (String suspect : suspects) {
                if (lower.contains(suspect)) { hits.add(service); break; }
            }
        }
        // Exact key spelling "exits" is intentional and observed in trace.
        return "{\"vInfo\":{\"exits\":" + (hits.isEmpty() ? "0" : "1")
                + ",\"id\":\"\"},\"systemService\":\"" + jsonEscape(hits.toString()) + "\"}";
    }

    @SuppressWarnings("unchecked")
    private static List<String> listServicesHidden() {
        try {
            Class<?> sm = Class.forName("android.os.ServiceManager");
            String[] a = (String[]) sm.getDeclaredMethod("listServices").invoke(null);
            List<String> out = new ArrayList<>();
            if (a != null) Collections.addAll(out, a);
            return out;
        } catch (Throwable ignored) { return Collections.emptyList(); }
    }

    public static String collectP2KeyStoreChain() {
        for (String alias : new String[]{"tomu_secure_v2", "tomu_secure"}) {
            try {
                KeyStore ks = KeyStore.getInstance("AndroidKeyStore");
                ks.load(null);
                if (!ks.containsAlias(alias)) continue;
                Certificate[] chain = ks.getCertificateChain(alias);
                if (chain == null) continue;
                StringBuilder out = new StringBuilder();
                for (Certificate cert : chain) {
                    out.append(Base64.encodeToString(cert.getEncoded(), Base64.NO_WRAP)).append(';');
                }
                return formEncode(out.toString());
            } catch (Throwable ignored) {}
        }
        return "";
    }

    public static String collectDefaultSms(Context c) {
        try {
            String pkg = Telephony.Sms.getDefaultSmsPackage(c);
            if (pkg == null) return "";
            PackageManager pm = c.getPackageManager();
            PackageInfo pi;
            if (Build.VERSION.SDK_INT >= 28) {
                pi = pm.getPackageInfo(pkg, PackageManager.GET_SIGNING_CERTIFICATES);
            } else {
                pi = pm.getPackageInfo(pkg, PackageManager.GET_SIGNATURES);
            }
            ApplicationInfo ai = pi.applicationInfo;
            String label = ai == null ? "" : ai.loadLabel(pm).toString();
            Signature sig = firstSignature(pi);
            String md5 = sig == null ? "" : md5Upper(sig.toCharsString().getBytes(StandardCharsets.UTF_8));
            long version = Build.VERSION.SDK_INT >= 28 ? pi.getLongVersionCode() : pi.versionCode;
            int flags = ai == null ? 0 : ai.flags;
            return pkg + "|" + label + "|" + md5 + "|" + version + "|" + flags;
        } catch (Throwable ignored) { return ""; }
    }

    private static Signature firstSignature(PackageInfo pi) {
        if (Build.VERSION.SDK_INT >= 28 && pi.signingInfo != null) {
            Signature[] s = pi.signingInfo.hasMultipleSigners()
                    ? pi.signingInfo.getApkContentsSigners()
                    : pi.signingInfo.getSigningCertificateHistory();
            return s == null || s.length == 0 ? null : s[0];
        }
        return pi.signatures == null || pi.signatures.length == 0 ? null : pi.signatures[0];
    }

    public static String collectDisplays(Context c) {
        try {
            DisplayManager dm = (DisplayManager) c.getSystemService(Context.DISPLAY_SERVICE);
            StringBuilder out = new StringBuilder();
            for (Display d : dm.getDisplays()) {
                String owner = null;
                try {
                    Field f = Display.class.getDeclaredField("mDisplayInfo");
                    f.setAccessible(true);
                    Object info = f.get(d);
                    Field ownerField = info.getClass().getDeclaredField("ownerPackageName");
                    ownerField.setAccessible(true);
                    owner = (String) ownerField.get(info);
                } catch (Throwable ignored) {}
                out.append(d.getName()).append('|').append(String.valueOf(owner)).append(';');
            }
            return out.toString();
        } catch (Throwable ignored) { return ""; }
    }

    public static String collectAudioJson(Context c) {
        AudioManager a = (AudioManager) c.getSystemService(Context.AUDIO_SERVICE);

                    .append(",\"cur\":").append(a.getStreamVolume(e.getValue())).append('}');
        }
        return s.append('}').toString();
    }

    public static String collectWidevine() {
        MediaDrm drm = null;
        try {
            drm = new MediaDrm(WIDEVINE);

            return "0:" + id + "|" + drm.getPropertyString(MediaDrm.PROPERTY_VENDOR)
