## 0.前言

这个壳子经常听人说，好像是frida检测特别厉害，据说国内许多银行类app都在用。逆向了一下发现非常简单，好在实现了第三代dex加固——代码抽取，刚好论坛里缺这方面的逆向帖子，这里简单补充一下。

## 1.SO脱壳

ida打开后发现有一个init_proc，这个函数是最早执行的，早于init_array里的函数，一般包含代码解密之类的逻辑：

 ![image](https://bbs.kanxue.com/upload/attach/202604/872365_C2J5MSRD2SWDZGK.webp)

第一个函数没什么用，mmap了一块空间，第二个函数点进去：

 ![image](https://bbs.kanxue.com/upload/attach/202604/872365_ZGAX88D228FYFYG.webp)

ida无法正常F5，是因为在代码里插入了数据：

 ![image](https://bbs.kanxue.com/upload/attach/202604/872365_MSK9J8DFQQNDWAS.webp)

不过无所谓，这部分主要是做了一下完整性检测，看看这部分代码有没有被篡改。核心是进入了sub_1095EC。

sub_1095EC主要做了以下几件事：

- 打开/proc/self/maps，定位到内存中的so的位置。
- 将so中加密的数据先解压缩，再异或解密。
- 将解密的数据回填到so内存。

所以这个加固的so壳非常简单，只需要在sub_1095EC执行完后，从内存中dump出so的rx段，回填即可：

 ![image](https://bbs.kanxue.com/upload/attach/202604/872365_QPJT5ZFSJX4PD8T.webp)

回填后可以发现这个加固很多符号名都没有去除，可以说做的相当简单。没有自定义linker，就是一个最简单的内存解密+原地回填。

 ![image](https://bbs.kanxue.com/upload/attach/202604/872365_B78TFVYFWY4PU3V.webp)

dex壳的知识点比较多，最核心的是dex文件相关的处理流程。

简单来说，andorid会将dex文件整体加载进内存，直到程序需要使用一个类的时候，才会去解析其在dex文件中具体的实现。

其中最核心的是一个类的代码，在dex文件中用code_item表示。

在dex文件的class_defines里，包含每个class对应的method，每个method指向data区的CodeItem，codeitem包含了一个函数的所有dex字节码。

如何在内存中获取到dex文件并进行修改？主要有两种方式：

1.通过Class类的dexCache获取，这种方式可以获取指定类所在的dex文件：

```python
jclass classClass = env->FindClass("类名");
if (!classClass) return;

// 获取 Class.dexCache (兼容不同版本)
jfieldID dexCacheField = env->GetFieldID(classClass, "dexCache", "Ljava/lang/DexCache;");
if (!dexCacheField) {
    if (env->ExceptionCheck()) env->ExceptionClear();
    dexCacheField = env->GetFieldID(classClass, "dexCache", "Ljava/lang/Object;");
    if (env->ExceptionCheck()) env->ExceptionClear();
}
if (!dexCacheField) return;

jobject dexCache = env->GetObjectField(targetClass, dexCacheField);
if (!dexCache) return;

// 获取 DexCache.dexFile (兼容 32/64 位)
jclass dexCacheClass = env->FindClass("java/lang/DexCache");
if (!dexCacheClass) return;

jlong dexFilePtr = 0;
jfieldID dexFileField = env->GetFieldID(dexCacheClass, "dexFile", "I");
if (dexFileField) {
    dexFilePtr = env->GetIntField(dexCache, dexFileField);
} else {
    if (env->ExceptionCheck()) env->ExceptionClear();
    dexFileField = env->GetFieldID(dexCacheClass, "dexFile", "J");
    if (env->ExceptionCheck()) env->ExceptionClear();
    if (!dexFileField) return;
    dexFilePtr = env->GetLongField(dexCache, dexFileField);
}

if (!dexFilePtr) return;

// dexFilePtr 就是 C++ DexFile* 指针
```

Java的CLass类包含了元素DexCache，DexCache包含了元素dexFile，通常为long，其值为dex文件在内存中的起始地址。

任意给一个类比如com.example.bb,通过FindClass可以获取其对应的Class类。然后依次访问上述元素，可以拿到com.example.bb类所在的dex文件：

 ![image](https://bbs.kanxue.com/upload/attach/202604/872365_5N54V6XU2TYN8UK.webp)

2.通过ClassLoader → DexPathList→ dexElements[] → DexFile → mCookie，获取所有已加载的dex文件。

也可以主动构造dexfile，添加到dexElements元素列表里，这样就实现了主动加载一个dex文件。

```python
// 获取 ClassLoader.pathList
jclass loaderClass = env->FindClass("dalvik/system/BaseDexClassLoader");
jfieldID pathListField = env->GetFieldID(loaderClass, "pathList", "Ldalvik/system/DexPathList;");
jobject pathList = env->GetObjectField(classLoader, pathListField);

// 获取 DexPathList.dexElements
jclass pathListClass = env->GetObjectClass(pathList);
jfieldID dexElementsField = env->GetFieldID(pathListClass, "dexElements", "[Ldalvik/system/DexPathList$Element;");
jobjectArray dexElements = (jobjectArray)env->GetObjectField(pathList, dexElementsField);

int count = env->GetArrayLength(dexElements);
for (int i = 0; i < count; i++) {
    jobject element = env->GetObjectArrayElement(dexElements, i);

    // 获取 Element.dexFile
    jclass elementClass = env->GetObjectClass(element);
    jfieldID dexFileField = env->GetFieldID(elementClass, "dexFile", "Ldalvik/system/DexFile;");
    jobject dexFile = env->GetObjectField(element, dexFileField);
    if (!dexFile) continue;

    // 获取 DexFile.mCookie (兼容不同版本)
    jclass dexFileClass = env->GetObjectClass(dexFile);
    jlong dexFilePtr = 0;

    // Android 8.0+: mCookie 是 Object (long[])
    jfieldID cookieField = env->GetFieldID(dexFileClass, "mCookie", "Ljava/lang/Object;");
    if (cookieField) {
        jlongArray cookieArray = (jlongArray)env->GetObjectField(dexFile, cookieField);
        if (cookieArray) {
            jlong *cookies = env->GetLongArrayElements(cookieArray, NULL);
            dexFilePtr = cookies[0];  // 第一个元素是 DexFile*
            env->ReleaseLongArrayElements(cookieArray, cookies, 0);
        }
    } else {
        // Android 5.0-7.x: mCookie 是 long
        if (env->ExceptionCheck()) env->ExceptionClear();
        cookieField = env->GetFieldID(dexFileClass, "mCookie", "J");
        if (cookieField) {
            dexFilePtr = env->GetLongField(dexFile, cookieField);
        } else {
            // Android 4.x: mCookie 是 int
            if (env->ExceptionCheck()) env->ExceptionClear();
            cookieField = env->GetFieldID(dexFileClass, "mCookie", "I");
            if (cookieField) {
                dexFilePtr = env->GetIntField(dexFile, cookieField);
            }
        }
    }

    if (env->ExceptionCheck()) env->ExceptionClear();
    if (!dexFilePtr) continue;

    // dexFilePtr 就是 C++ DexFile* 指针
    // 可以通过 DexFile->begin_ 获取原始 DEX 数据
}
```

由于不同版本andorid的实现方式不同，所以要兼容各个版本的实现。主要是mCookie的类型在变。

### 3.5 回填代码

代码抽取壳的实现方式有多种，核心如何隐藏dex文件中的codeitem。

- 可以通过hook linkcode来在findclass->defineclass第一次加载类的时候回填。
- 可以在dex文件加载到内存后，手动获取的dex文件，然后手动回填code。

只要不在opencommon等地方出现完整的dex，即可实现代码抽取的效果。

这个加固使用的是第二种方式。

首先在dex文件里的code_off对应的数据置空

 ![image](https://bbs.kanxue.com/upload/attach/202604/872365_VGY76JVDX8HBR4S.webp)

可以看到code中有大量的0。

其实真实的code在dex文件的其他地方，手动修改code_off指向正确的偏移即可。

 ![image](https://bbs.kanxue.com/upload/attach/202604/872365_H4ADAVTPGXKA2C6.webp)

通过代码中的BBbb.dgc定位到所有被抽取的code地方：

 ![image](https://bbs.kanxue.com/upload/attach/202604/872365_FD9PACF75UFUPAT.webp)

定位到dex文件末尾的BBbb.dgc，大端法读取前一个4字节数0x2a4c20。

BBbbdgc的起始地址减0x20再减该值，定位到真实的code起点：

0x16b3550-0x20-0x2a4c20 = 0x140E910

 ![image](https://bbs.kanxue.com/upload/attach/202604/872365_YMJUU4RE49BST4F.webp)

其中前0x18个字节为header，第0xc的int为抽取的元结构的总大小，0x8为每个结构的大小，0x67de8 / 0x18 = 0x453F 代表有0x453F个函数被抽取。0x67e00为函数相对0x140E910的起始偏移。所以真实的code起始位0x140E910 + 0x67e00 = 0x1476710

接下来每0x18个字节为一组，第一个int表示代码的偏移，第二个int表示代码的大小，第0x10偏移处的int表示需要写回dex文件的地方。

以第一个结构为例，表示需要将dex文件偏移0x1f8754处写入（0x1476710+0x0）

实际上这是在修正code_off字段，换成真实的代码偏移：

 ![image](https://bbs.kanxue.com/upload/attach/202604/872365_HREV4N6727GJCG8.webp)

可以对比抽取后的：

 ![image](https://bbs.kanxue.com/upload/attach/202604/872365_FJ4JB8DNHFV6JP9.webp)

写入的时候注意需要按照uleb128格式写入，这是dex文件中常见的数据编码格式：

 ![image](https://bbs.kanxue.com/upload/attach/202604/872365_UBNVKPHTMTDDCXU.webp)

至此，dex文件被正常加载，抽取的代码被通过“重定位”的方式回填。原app的逻辑可以开始正常运行。

完整的纯算法dex还原代码：

```python
import struct
import zlib
import zstandard
from gmssl.sm4 import CryptSM4, SM4_DECRYPT

def sm4_decrypt_ecb_nopad(key, ciphertext):
    sm4 = CryptSM4()
    sm4.set_key(key, SM4_DECRYPT)
    output = []
    for i in range(0, len(ciphertext), 16):
        block = list(ciphertext[i:i + 16])
        output += sm4.one_round(sm4.sk, block)
    return bytes(output)

def write_uleb128(dex,offset,value):
    count = 0
    while value >> 7:
        dex[offset + count] = (value & 0x7F) | 0x80
        value >>= 7
        count += 1
        if count == 4:
            dex[offset + count] = value & 0x7F
            return count + 1

    dex[offset + count] = value | 0x80
    return count + 1

def dex_codeitem_relocate(dex):
    magic = b"BBbb.dgc"
    length = len(dex)
    off = length - len(magic)
    while True:
        if magic == dex[off:off+len(magic)]:
            break
        else:
            off = off - 1
    off1 = struct.unpack(">I",dex[off-4:off])[0]
    code_map_start = off - 0x20 - off1
    item_size = struct.unpack(">I",dex[code_map_start+8:code_map_start+0xc])[0]
    itemdata_len = struct.unpack(">I",dex[code_map_start+0xc:code_map_start+0x10])[0]
    data_off = struct.unpack(">I",dex[code_map_start+0x10:code_map_start+0x14])[0]
    item_count = itemdata_len // item_size
    dex = bytearray(dex)
    for i in range(item_count):
```

## 4.总结

这个加固其实不难，总共逆向分析大概2天时间。so层加固非常简单，没有混淆，没有自定义linker，检测手段也比较常规，字符串加密为inline方式。dex加固方式采用第三代代码抽取加固，可以对抗常规的脱壳脚本。frida检测之所以以前觉得很强，可能是因为从检测java-bridge角度出发的。但是frida17以后没有这个特征了，把端口换到30000+应该就能绕过。
